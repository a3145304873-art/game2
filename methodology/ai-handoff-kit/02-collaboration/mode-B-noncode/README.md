# 模式 B：非代码交付模式（总览）

> 适用对象：**不写代码、只交付合格文档**的合作同学（产品 / 运营 / 其他部门）。
>
> 这是本协同规范的核心模式。下面先给全貌，详细操作见 `01` ~ `05`。

---

## 1. 模式定位

协作者拿到接收方提供的最新 main 源码 + 本规范 + 一份需求 Issue，借助 Claude Code 把需求分析清楚、把实现方案写明白，交付**三类标准化文档**。接收方基于这些文档做对齐审核、Spec 验收，再自行完成代码开发。

**核心思想**：协作者负责「想清楚 + 写明白」，接收方负责「判对错 + 写代码」。代码不经过协作者之手，但代码要实现什么、怎么实现，由协作者的文档定义。

---

## 2. 交付物清单（三类文档）

| 交付物 | 文件 | 回答的问题 | 来源 |
|--------|------|-----------|------|
| **技术规格书** | `SPEC.md` | 做什么？做到什么程度（验收标准）？ | `/kickoff` Phase 1 |
| **任务计划** | `PLAN.md` + `TASKS.md` | 技术上怎么做？拆成哪些任务？ | `/kickoff` Phase 2-3 |
| **代码逻辑差异分析** | `DIFF-ANALYSIS.md` | 当前 main 代码是怎样的？要改哪些地方？风险在哪？ | 协作者额外产出（模式 B 独有） |

> PLAN 与 TASKS 合称「Task Plan」。SPEC / PLAN / TASKS 由 `/kickoff` 自动产出并审核；DIFF-ANALYSIS 是模式 B 独有的额外文档，由协作者在理解 main 代码后单独撰写。

---

## 3. 端到端流程

```
[接收方]                                          [协作者]
   │
   ├─ ① 同步最新 main 源码            ──────→  （见 01-接收方准备）
   ├─ ② 提供 collaboration/ 规范
   ├─ ③ 写需求 Issue（用 ISSUE 模板）
   │ ─────────────────────────────────────────→
   │                                                ├─ ④ 通读本目录 01~05（见 02-操作流程）
   │                                                ├─ ⑤ 与 Claude Code 几轮交互，说清需求
   │                                                ├─ ⑥ AI 做 Issue 分析，对比 main 代码
   │                                                ├─ ⑦ 跑 /kickoff：
   │                                                │     SPEC → SPEC审核 →
   │                                                │     PLAN → PLAN审核 →
   │                                                │     TASKS → TASKS审核 →
   │                                                │     一致性审核  ← 四步独立审核在此完成
   │                                                ├─ ⑧ 撰写 DIFF-ANALYSIS.md（代码差异分析）
   │                                                ├─ ⑨ 复核一致性（差异分析与前三份对齐）
   │                                                └─ ⑩ 按 DELIVERABLE-CHECKLIST 自检，打包交付
   │ ←─────────────────────────────────────────
   ├─ ⑪ 对齐审核（用 05-alignment-review）   ← 协作者交付到此结束
   ├─ ⑫ 最终 Spec 验收
   └─ ⑬ 接收方做代码开发、发版
```

**协作者终点 = 步骤 ⑩**。

---

## 4. 四步独立审核（协作者必做）

四步审核对应 `/kickoff` 的 Phase 1.2 / 2.2 / 3.2 / 4，**全部由独立 AI Agent 完成**（审核 Agent 与写作过程上下文隔离，不是"自己审自己"）：

| 步骤 | 审核对象 | 执行 Agent | 通过标志 | 轮次上限 |
|------|---------|-----------|---------|---------|
| ① | `SPEC.md` | spec-reviewer | `.spec-passed` | 5 |
| ② | `PLAN.md` | plan-reviewer | `.plan-passed` | 5 |
| ③ | `TASKS.md` | tasks-reviewer | `.tasks-passed` | 5 |
| ④ | SPEC+PLAN+TASKS（+差异分析）交叉一致 | consistency-reviewer | `.consistency-passed` | 2 |

**当 `.consistency-passed` marker 出现，四步审核全部完成，协作者立即停止**——不继续 `/kickoff` 的后续阶段（readiness / alignment / implement），那些由接收方接手。详见 [04-四步独立审核.md](./04-四步独立审核.md)。

> **对齐审核（alignment）由接收方做，不在协作者四步内。** 这是本模式最重要的职责边界。

---

## 5. 关键原则

1. **需求驱动，文档先行**：协作者不写一行业务代码，所有"要做什么"都落在文档里。
2. **审核独立**：四步审核由独立 Agent 执行，协作者不能跳过或自己签字。
3. **对比现状**：所有方案必须基于"当前 main 代码实际是怎样的"，不能凭空设计。DIFF-ANALYSIS 是锚点。
4. **边界清晰**：SPEC 要写清 Out of Scope；不做什么和做什么一样重要。
5. **可验收**：每个需求都有 GIVEN/WHEN/THEN 形式的验收标准（AC），接收方能据此判断"做完了没"。
6. **变更回退**：撰写过程中若发现需求本身有误，停止写作，回到接收方澄清，不带着错误理解硬写。

## 7. 协作者最少必要知识

如果你时间有限，至少记住这三点：

1. **你要交付的是文档，不是代码**。用 Claude Code 帮你分析需求、对比代码、写文档，但不要让它写业务代码。
2. **跑 `/kickoff`，看到 `.consistency-passed` 就停**。四步审核自动完成，停在那里交付。
3. **额外写一份《代码逻辑差异分析》**，说清当前 main 代码现状和要改哪里。这是你交付物里最体现价值的一份。
