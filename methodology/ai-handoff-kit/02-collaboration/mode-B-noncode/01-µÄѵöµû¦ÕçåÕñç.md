# 01 · 接收方准备（派发需求前）

> 受众：**接收方（项目负责人）**。在把需求交给协作者之前，按本文件逐项准备好。

---

## 准备清单

派发一个模式 B 需求前，接收方必须完成以下 6 项：

| # | 准备项 | 完成标志 |
|---|--------|---------|
| 1 | 同步最新 main 源码给协作者 | 协作者本地拿到与当前主干一致的代码 |
| 2 | 提供 `collaboration/` 规范 | 协作者已读 `mode-B-noncode/` 全部文档 |
| 3 | 写需求 Issue | 用 [ISSUE 模板](../templates/ISSUE.template.md)，含背景/目标/范围/验收标准 |
| 4 | 明确协同参数 | 模式（B）、deadline、优先级、接收方对接人 |
| 5 | 确认协作者环境 | 已装 Claude Code + spec-workflow，能跑 `/kickoff` |
| 6 | 约定交付方式 | 文档放哪、如何回传、对齐审核排期 |

---

## 1. 同步最新 main 源码

协作者需要**当前最新的 main 代码**作为分析基础（尤其是 DIFF-ANALYSIS 要对比现状）。

- **方式**：内部 git 克隆、打包 zip、或共享目录拷贝均可。
- **关键**：协作者拿到的必须是**主干 main 分支**，不是某个 feat 分支或正式服历史版本。
- **告知协作者代码结构**：指向仓库根 `CLAUDE.md` 的「架构概览」「核心数据流」，让其快速理解 backend / frontend / data / specs 的组织。

> 注意：源数据库（`data/*.db`）体积较大且为只读资产。协作者主要需要**代码**和**结构**做差异分析，不一定需要完整数据库；如需跑通项目验证想法，再提供数据库。

---

## 2. 提供 collaboration/ 规范

把整个 `collaboration/` 目录给协作者，要求其**至少通读**：
- 根 [README.md](../README.md)
- 本目录 [README.md](./README.md)
- [02-协作者操作流程.md](./02-协作者操作流程.md)
- [03-交付物规范.md](./03-交付物规范.md)

其余按需查阅。

---

## 3. 写需求 Issue

这是协作者工作的**起点和唯一需求来源**。质量直接决定后续所有文档的质量。

**必须用** [templates/ISSUE.template.md](../templates/ISSUE.template.md)，至少包含：

| 字段 | 要求 |
|------|------|
| **背景与动机** | 为什么要做？解决什么痛点？给协作者足够的业务上下文 |
| **目标** | 做成什么样？用可观测的语言描述（不是"优化体验"，而是"输入超 5000 字时禁用发送并提示"） |
| **范围** | 明确 In Scope 和 Out of Scope。不做什么要写清楚 |
| **验收标准** | 每条用 GIVEN/WHEN/THEN 或可测试语句。这是后续 SPEC 的 AC 来源 |
| **约束** | 性能、兼容、安全、不能碰的红线（如"不能改正式服端口""源 DB 只读"） |
| **参考** | 相关历史 spec、相关代码路径、类似功能 |

> **Issue 质量红线**：如果验收标准模糊到无法测试，协作者应在步骤 ⑤ 反馈澄清，而不是自行猜测。接收方要欢迎这种反馈。

---

## 4. 明确协同参数

在 Issue 里或沟通中明确：
- **模式**：本需求走模式 B（非代码交付）。
- **deadline**：期望交付日期。
- **优先级**：高/中/低，影响协作者排期。
- **接收方对接人**：协作者有疑问时找谁（通常即接收方本人）。
- **是否需要中间同步**：是否要求协作者在 SPEC 完成、PLAN 完成等节点同步确认（推荐至少 SPEC 完成时同步一次，避免方向跑偏）。

---

## 5. 确认协作者环境

协作者需要以下环境（提供安装指引，别假设对方会）：

### 5.1 Claude Code
- 安装 Claude Code CLI（Anthropic 官方）。
- 确认能正常启动、能读项目目录。

### 5.2 spec-workflow（关键）
本模式的四步审核依赖 spec-workflow 命令（`/kickoff` 及其审核 Agent）。协作者**必须安装**：

- 安装脚本：`~/.spec-workflow/install.sh`（由接收方提供，或告知获取方式）。
- 安装后可用命令：`/kickoff` `/write-spec` `/write-plan` `/write-tasks` `/review` 等。
- 可用审核 Agent：`spec-reviewer` `plan-reviewer` `tasks-reviewer` `consistency-reviewer` `alignment-reviewer` 等。

> 若协作者无法安装 spec-workflow，降级方案：跳过 Agent 审核，改用 [checklists/](../checklists/) 的人工 checklist 逐项核对。但这会降低质量保障，**需接收方知情同意**，并在交付时加强对齐审核力度。

### 5.3 项目运行环境（可选）
若协作者需要跑通项目验证想法（非必须，DIFF-ANALYSIS 主要靠读代码）：
- Python 3.x + `requirements.txt` 依赖
- Node.js + `npm install`
- `.env` 配置（API key 等，由接收方提供）

---

## 6. 约定交付方式

- **文档存放**：建议协作者在自己环境的 `specs/{N}-{slug}/` 下产出（`/kickoff` 默认路径），完成后整体回传给接收方。
- **回传方式**：打包 `specs/{N}-{slug}/` 整个目录（含 SPEC/PLAN/TASKS/DIFF-ANALYSIS + reviews/ + 各 marker）给接收方。
- **对齐审核排期**：接收方收到后何时做对齐审核，提前告知协作者。

## 派发模板（可直接复制给协作者）

```
【需求派发 · 模式 B 非代码交付】

需求 Issue：见附件 ISSUE.md（或 POPO/文档链接）
main 源码：见附件 / 共享路径 XXX
协同规范：见附件 collaboration/ 目录，请先通读 mode-B-noncode/
模式：B（只交付文档，不写代码）
deadline：2026-XX-XX
优先级：中
对接人：N8872

请按 collaboration/mode-B-noncode/02-协作者操作流程.md 执行。
四步独立审核完成（.consistency-passed 出现）后，连同 DIFF-ANALYSIS.md 一起交付。
SPEC 草稿完成后请先同步我一次，确认方向再继续。
```

## 接收方自查

派发前，接收方自己确认：
- [ ] main 源码已同步且为最新主干
- [ ] collaboration/ 规范已提供
- [ ] Issue 已写，验收标准可测试
- [ ] 协作者已知模式 B、deadline、对接人
- [ ] 协作者环境（Claude Code + spec-workflow）已就绪
- [ ] 交付方式与对齐审核排期已约定
