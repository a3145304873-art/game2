# 02 · 协作者操作流程（逐步指南）

> 受众：**协作者（合作同学）**。从启动 Claude Code 到交付文档的完整步骤。照做即可，每步都给了可直接复制的话术。

---

## 前置确认（开始前花 5 分钟检查）

| # | 检查项 | 如何确认 |
|---|--------|---------|
| 1 | Claude Code 已安装 | 终端能跑 `claude` 命令 |
| 2 | spec-workflow 已安装 | Claude Code 里能识别 `/kickoff` 命令（输入 `/` 看列表） |
| 3 | main 源码已到手 | 本地有 main 代码目录（含 backend/frontend/data/specs 等） |
| 4 | collaboration/ 规范已到手 | 本地有 collaboration/ 目录 |
| 5 | 需求 Issue 已到手 | 有 ISSUE.md 或接收方给的需求说明 |

任一项缺失 → 先找接收方（对接人）补齐，不要硬开始。

---

## Step 0 · 准备工作目录

1. 把接收方给的 **main 源码**解压/放到本地一个固定目录，例如 `D:\work\ai-copywriter-main\`。
2. 把 **collaboration/ 规范**和 **ISSUE.md** 放到这个目录下（或旁边，能被 Claude Code 访问）。
3. 在 **main 源码根目录**启动 Claude Code——这样 AI 既能跑 `/kickoff`（产出落在 `specs/`），又能读 `backend/` `frontend/` 代码做差异分析。

> 为什么要在 main 源码根目录启动？因为《代码逻辑差异分析》必须基于真实的 main 代码。AI 看不到代码就写不出有价值的差异分析。

---

## Step 1 · 让 AI 读取规范与需求

启动 Claude Code 后，第一条指令让它建立上下文。**直接复制下面的话术**：

```
我是模式 B 协作者，负责非代码交付。请依次阅读以下内容，理解我的任务和交付规范：

1. collaboration/README.md（协同规范总览）
2. collaboration/mode-B-noncode/README.md（模式 B 总览）
3. collaboration/mode-B-noncode/02-协作者操作流程.md（本操作流程）
4. collaboration/mode-B-noncode/03-交付物规范.md（交付物要求）
5. collaboration/mode-B-noncode/04-四步独立审核.md（审核要求）
6. ISSUE.md（我的需求）

读完后用 3 句话向我复述：我要做什么、交付什么、在哪里停止。确认无误后我们进入需求澄清。
```

AI 复述后，核对它是否理解正确。理解偏了就纠正。

---

## Step 2 · 需求澄清（几轮交互）

AI 会基于 ISSUE.md 向你提问（这是 `/kickoff` 的需求确认环节）。问题通常围绕：
- 范围边界（要不要做 X？）
- 涉及的角色/场景
- 边界与异常情况
- 隐含假设
- 成功指标

**你的回答原则**：
- **不确定就问接收方**，不要自己猜。AI 问的问题如果你答不准，记下来，暂停去问对接人，回来再继续。
- **用业务语言答**，不要编造技术细节（技术方案是 AI 和后续流程的事）。
- 几轮后 AI 会汇总一份需求确认（REQUIREMENTS），你确认"没问题"才进入下一步。

> 推荐在 **SPEC 草稿完成时**同步接收方看一眼方向，避免写完一大堆才发现跑偏。接收方通常也欢迎这个中间确认点。

---

## Step 3 · AI 做 Issue 分析（对比 main 代码）

这是体现协作者价值的关键环节。让 AI 深入理解当前 main 代码，为差异分析打基础。

**话术**：
```
现在请做 Issue 分析：对照我的需求（ISSUE.md + 刚确认的需求），深入阅读当前 main 代码，
找出：
1. 需求涉及的功能，当前 main 代码是怎么实现的？（列出关键文件、函数、数据流）
2. 当前实现与需求的差距在哪？哪些要新增、哪些要修改、哪些要删除？
3. 有哪些风险点、技术债、需要注意的约束（如只读数据库、端口规范等）？

先给我一份口头分析，不要急着写正式文档。我确认你的理解对了，再进入正式规划。
```

AI 给出分析后，**核对它是否真的读了代码**（应该能说出具体的文件名、函数名、当前逻辑）。如果说得很泛、没有具体代码引用，要求它"请引用具体的文件路径和函数，证明你读过代码"。

---

## Step 4 · 跑 /kickoff（自动产出 SPEC / PLAN / TASKS + 四步审核）

理解对齐后，正式启动规划流程。**话术**：
```
请运行 /kickoff，基于 ISSUE.md 和已确认的需求，完成规划。

重要：这是模式 B 非代码交付。/kickoff 跑到 Phase 4 一致性审核通过即停止，
不要进入 Phase 5 readiness、Phase 5.6 alignment，也不要进入 implement/QA/merge。
当 .consistency-passed marker 出现，四步独立审核全部完成，立即停止并通知我。
```

`/kickoff` 会自动执行：

| 阶段 | 产出 | 审核 | 通过标志 |
|------|------|------|---------|
| Phase 1 | `SPEC.md` | spec-reviewer | `.spec-passed` |
| Phase 2 | `PLAN.md` | plan-reviewer | `.plan-passed` |
| Phase 3 | `TASKS.md` | tasks-reviewer | `.tasks-passed` |
| Phase 4 | （交叉一致性） | consistency-reviewer | `.consistency-passed` |

**这四步审核由独立 Agent 完成，你不用手动审，但要知道每步的通过标志。**

- 某步审核 **FAIL**：AI 会自动修改文档并重审（有轮次上限：SPEC/PLAN/TASKS 各 5 轮，一致性 2 轮）。
- **达到轮次上限仍 FAIL**：AI 会停下来把问题交给你。此时把问题转给接收方一起判断（可能是需求本身有矛盾）。
- **看到 `.consistency-passed`**：四步全过，**停止**，进入 Step 5。

> 中途如果你想看某份文档，随时让 AI 展示当前 SPEC.md / PLAN.md / TASKS.md 内容。

---

## Step 5 · 撰写《代码逻辑差异分析》（DIFF-ANALYSIS.md）

这是 `/kickoff` 不产出、需要你单独完成的交付物，也是模式 B 区别于普通 spec-workflow 的核心。

**话术**：
```
现在请撰写《代码逻辑差异分析》(DIFF-ANALYSIS.md)，使用
collaboration/templates/DIFF-ANALYSIS.template.md 模板。

基于 Step 3 的 Issue 分析 + 刚产出的 SPEC/PLAN/TASKS，说明：
1. 现状：需求涉及的功能，当前 main 代码如何实现（文件/函数/数据流）
2. 改动点：要新增/修改/删除哪些代码，逐项列出（文件路径 + 改动说明）
3. 影响面：改动会影响哪些现有功能、上下游
4. 风险与约束：技术风险、需注意的项目约束（只读 DB、端口、进程保护等）
5. 不改什么：明确不在本次改动范围的代码

注意：只分析、不写代码。给接收方看懂"要改哪里、为什么"，由接收方决定怎么改。
```

写完后通读一遍，确认：
- 每个改动点都有**具体的文件路径**（不是泛泛而谈）
- 与 SPEC 的 FR、TASKS 的任务**一一对应**，没有脱节
- 风险写得诚实，不藏着

详见 [03-交付物规范.md](./03-交付物规范.md) 的 DIFF-ANALYSIS 部分。

---

## Step 6 · 复核一致性（差异分析 vs 前三份）

DIFF-ANALYSIS 写完后，让 consistency-reviewer 再审一次，确保四份文档完全对齐：

**话术**：
```
请用 consistency-reviewer 重新审核一致性，这次把 DIFF-ANALYSIS.md 也纳入，
检查 SPEC ↔ PLAN ↔ TASKS ↔ DIFF-ANALYSIS 四份文档是否完全对齐：
- SPEC 的每条 FR 是否在 PLAN/TASKS/DIFF 中都有对应？
- TASKS 的每个任务是否在 DIFF 中有对应的改动点？
- DIFF 提到的改动是否都在 TASKS 范围内、没有遗漏或越界？
- 四份文档的术语、边界（Out of Scope）是否一致？
```

若不一致，修正后重审，直到一致。

---

## Step 7 · 交付自检 + 打包

**话术**：
```
请按 collaboration/templates/DELIVERABLE-CHECKLIST.template.md 逐项自检本次交付，
列出已具备和缺失的交付物，确认全部齐备后告诉我可以打包了。
```

自检通过后，打包交付：

```
交付内容（specs/{N}-{slug}/ 整个目录）：
├── REQUIREMENTS.md          （/kickoff 产出的需求确认）
├── spec.md / SPEC.md        （技术规格书）
├── plan.md / PLAN.md        （技术实现计划）
├── tasks.md / TASKS.md      （任务分解）
├── DIFF-ANALYSIS.md         （代码逻辑差异分析）← 模式 B 独有
├── reviews/                 （四步审核报告）
├── .spec-passed             （四步审核通过标志）
├── .plan-passed
├── .tasks-passed
└── .consistency-passed
```

把这个目录整体回传给接收方，并附一句说明："模式 B 交付完成，四步独立审核已过（.consistency-passed），请做对齐审核。"

---

## 流程速记（贴在显示器上）

```
读规范 → 澄清需求 → AI 分析 main 代码 → 跑 /kickoff
→ 看到 .consistency-passed 就停 → 写 DIFF-ANALYSIS → 复核一致性
→ 自检清单 → 打包 specs/{N}/ 交付
```

**三个绝不**：
1. 绝不写业务代码（只写文档）。
2. 绝不跳过审核（四步必须全过）。
3. 绝不在 .consistency-passed 后继续跑（readiness/alignment/implement 是接收方的事）。
