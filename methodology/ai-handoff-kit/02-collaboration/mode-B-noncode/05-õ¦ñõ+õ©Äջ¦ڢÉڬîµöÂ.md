# 05 · 交付与对齐验收

> 受众：**双方**。前半部分（交付）给协作者，后半部分（对齐验收 + 代码衔接）给接收方。

---

## 第一部分 · 协作者交付

### 1. 交付前自检

用 [templates/DELIVERABLE-CHECKLIST.template.md](../templates/DELIVERABLE-CHECKLIST.template.md) 逐项核对。**全部勾选才能交付**：

- [ ] `SPEC.md` 存在且通过 spec-reviewer（`.spec-passed`）
- [ ] `PLAN.md` 存在且通过 plan-reviewer（`.plan-passed`）
- [ ] `TASKS.md` 存在且通过 tasks-reviewer（`.tasks-passed`），含 Coverage Matrix
- [ ] `DIFF-ANALYSIS.md` 存在，每个改动点有具体文件路径
- [ ] 四份文档通过一致性审核（`.consistency-passed`），且一致性复审已纳入 DIFF-ANALYSIS
- [ ] `REQUIREMENTS.md` 存在（/kickoff 产出的需求确认）
- [ ] `reviews/` 目录含四步审核报告
- [ ] 四份文档术语、边界（Out of Scope）一致
- [ ] 无业务代码被写入（模式 B 只交付文档）
- [ ] 已通读全部文档，无错别字、无 TODO 残留

### 2. 打包

交付 `specs/{N}-{slug}/` **整个目录**，包含：

```
specs/{N}-{slug}/
├── REQUIREMENTS.md          需求确认
├── spec.md                  技术规格书
├── plan.md                  技术实现计划
├── tasks.md                 任务分解
├── DIFF-ANALYSIS.md         代码逻辑差异分析 ★
├── reviews/                 四步审核报告
├── .spec-passed             四步审核通过标志
├── .plan-passed
├── .tasks-passed
└── .consistency-passed
```

### 3. 回传与说明

把整个目录打包回传接收方，附简短交付说明：

```
【模式 B 交付】

需求：{Issue 标题}
spec 目录：specs/{N}-{slug}/
四步独立审核：全部通过（.consistency-passed）
DIFF-ANALYSIS：已含，改动点 X 处，涉及文件 Y 个
已知风险/需确认点：{列出 DIFF 中标注"需接收方确认"的项}

请做对齐审核。如有问题我随时配合修订。
```

**协作者职责到此结束。** 后续由接收方接手。

---

## 第二部分 · 接收方对齐验收

### 4. 对齐审核（alignment review）★ 接收方专属

> 这一步**只由接收方做**，是模式 B 最重要的质量关卡——判断"协作者的产出是否忠实于原始需求意图"。

**做法**：用 alignment-reviewer（或对照 [checklists/05-alignment-review.md](../checklists/05-alignment-review.md)）审核，输入 = 原始 ISSUE.md + REQUIREMENTS.md + 四份交付文档。

**核心判断**：
| 维度 | 问题 |
|------|------|
| **意图忠实** | 产出是否解决了 ISSUE.md 提出的真实问题？有没有跑题、自嗨？ |
| **范围一致** | 做的是不是 Issue 要的范围？有没有擅自扩大或缩小？ |
| **假设合理** | 协作过程中的假设（尤其 `[auto-decided]`）是否成立？ |
| **可落地** | 接收方基于这批文档，能不能顺畅写代码？有没有悬空、矛盾？ |
| **DIFF 可信** | DIFF-ANALYSIS 的代码引用是否准确（真的对得上 main 代码）？ |

**对齐审核结果**：

- **PASS** → 进入 Spec 验收（第 5 步）。
- **FAIL（方向跑偏）** → 两种处理：
  - **小修**：让协作者按对齐审核意见修订文档，重走一致性审核后重新交付。
  - **大改（需求理解有误）** → 接收方重新澄清需求，协作者走 `/kickoff` REDO 流程重做（备份原产出 → 清 marker → 重跑 Phase 1-4）。

### 5. 最终 Spec 验收

接收方对 SPEC.md 做**最终签字**：
- [ ] 每条 FR 都符合预期，且可实现
- [ ] 每条 AC 都可测试，且是真正想要的验收点
- [ ] Out of Scope 确实不在本次范围
- [ ] 技术方案（PLAN）接收方认可，能据此实现
- [ ] TASKS 的任务划分接收方接受
- [ ] DIFF-ANALYSIS 的改动点接收方确认无误

**签字方式**：将 spec.md frontmatter 的 `status` 改为 `accepted`（或建立 `.spec-accepted` 标志），注明验收人与日期。

### 6. 代码开发衔接（接收方接手）

验收通过后，**模式 B 正式结束**，进入接收方的代码开发：

1. 接收方基于验收的 SPEC + PLAN + TASKS + DIFF-ANALYSIS，在自己的 main worktree 创建 `feat-*` 分支。
2. 按 TASKS 逐任务实现代码（此时可复用项目完整的 spec-workflow：`/implement-spec` → `/review` → `/qa` → `/merge-ready`）。
3. DIFF-ANALYSIS 作为"改动地图"，加速定位代码。
4. 实现完成走正常 merge 流程（仓库根 CLAUDE.md「Merge 到主干的 Checklist」）。
5. 合并、打 tag、升版本号、发版。

> 此时协作者已不参与。但若实现中发现 SPEC/PLAN 有歧义，接收方可回溯找协作者澄清——这就是为什么交付文档要清晰、可追溯。

## 全流程责任矩阵

| 阶段 | 协作者 | 接收方 |
|------|--------|--------|
| 需求派发 | — | 准备源码/规范/Issue |
| 需求澄清 | 描述需求、答疑问 | 答协作者疑问 |
| Issue 分析 | 让 AI 对比 main 代码 | — |
| SPEC/PLAN/TASKS | 跑 /kickoff 产出 | （可选）SPEC 完成时看方向 |
| 四步独立审核 | 盯 marker、达上限升级 | — |
| DIFF-ANALYSIS | 撰写 + 复核一致性 | — |
| 交付 | 自检 + 打包 + 回传 | — |
| 对齐审核 | — | alignment-reviewer 把关 |
| Spec 验收 | — | 最终签字 |
| 代码开发 | — | 实现 + merge + 发版 |
