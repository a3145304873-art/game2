# 03 · 交付物规范（三类文档怎么写）

> 受众：**协作者**。说明四份交付文档（SPEC / PLAN / TASKS / DIFF-ANALYSIS）各写什么、怎么写、常见错误。SPEC/PLAN/TASKS 由 `/kickoff` 自动产出并审核，本文帮你理解它们该长什么样；DIFF-ANALYSIS 需你手动撰写，重点讲。

---

## 总览

| 文档 | 回答 | 模板 | 产出方式 |
|------|------|------|---------|
| SPEC.md | 做什么？做到什么程度？ | [SPEC.template.md](../templates/SPEC.template.md) | `/kickoff` 自动 |
| PLAN.md | 技术上怎么做？ | [PLAN.template.md](../templates/PLAN.template.md) | `/kickoff` 自动 |
| TASKS.md | 拆成哪些可执行任务？ | [TASKS.template.md](../templates/TASKS.template.md) | `/kickoff` 自动 |
| DIFF-ANALYSIS.md | 当前代码怎样？要改哪里？ | [DIFF-ANALYSIS.template.md](../templates/DIFF-ANALYSIS.template.md) | **你手动写** |

**四份文档必须相互对齐、可交叉追溯**——这是 Step 6 一致性审核的检查重点。

---

## 一、SPEC.md（技术规格书）

### 目的
定义"做什么"和"做到什么程度"。这是接收方验收的依据，也是后续代码开发的纲领。

### 必含 6 段（对应 spec-workflow 标准）

| 段落 | 内容 | 要点 |
|------|------|------|
| **背景与动机** | 为什么要做、解决什么问题 | 给足业务上下文，让没参与过的人也能懂 |
| **详细需求 (FR-XX)** | 功能需求逐条列出 | 每条用 `SHALL / SHALL NOT`，编号 FR-01、FR-02… |
| **验收标准 (AC-XX)** | 每个需求怎么验收 | 用 GIVEN/WHEN/THEN 格式，可测试 |
| **技术方案** | 大致怎么实现 | 高层方案，不需到代码细节（那是 PLAN 的事） |
| **边界与异常** | 异常情况如何处理 | 错误场景、降级方案 |
| **范围边界 (Out of Scope)** | 明确不做什么 | 和"做什么"一样重要，防止需求蔓延 |

### 格式要求
- 文件头 frontmatter：`id / title / status / priority / created / updated`
- 参考真实样例：`specs/006-fix-long-announcement-crash/spec.md`

### 常见错误
| 错误 | 后果 | 正确做法 |
|------|------|---------|
| FR 写得像口号（"优化体验"） | 无法验收、无法实现 | 写成可观测行为（"输入超 5000 字时禁用发送"） |
| 缺 Out of Scope | 需求无限蔓延 | 明确列出"本次不做 X、Y、Z" |
| AC 不可测试 | 接收方无法验收 | 用 GIVEN/WHEN/THEN，写明前后状态 |
| FR 和 AC 对不上 | 需求有空洞 | 每个 FR 至少有一条 AC 覆盖 |

## 二、PLAN.md（技术实现计划）

### 目的
定义"技术上怎么做"。把 SPEC 的需求落到技术方案上。

### 必含 7 段（对应 spec-workflow 标准）

| 段落 | 内容 |
|------|------|
| **Technical Approach** | 整体技术方案、架构选型 |
| **Data Model** | 涉及的数据结构、表结构变更 |
| **API Contracts** | 新增/修改的接口契约（路径、入参、出参） |
| **Key Decisions** | 关键决策点，每个决策给 ≥2 备选 + 选定理由 |
| **Risks** | 技术风险及应对 |
| **Testing** | 测试策略（单元/集成/E2E） |
| **Dependencies** | 依赖的外部库、服务、其他 spec |

### 格式要求
- Key Decisions **必须给备选方案**（≥2 个），不能只写一个"就这么做"。
- API Contracts 要具体到入参出参字段，不能只写"加个接口"。

### 常见错误
- 决策无备选 → 违反 spec-workflow，plan-reviewer 会打回。
- 方案脱离 main 现状 → 接收方按 PLAN 实现时发现对不上代码。**必须对照 DIFF-ANALYSIS**。

---

## 三、TASKS.md（任务分解）

### 目的
把 PLAN 拆成**原子任务**，每个任务可独立执行、独立验证。这是接收方写代码时的施工清单。

### 必含要素

| 要素 | 说明 |
|------|------|
| **Phase 分组** | 任务按阶段分组（如 Phase 1 后端、Phase 2 前端、Phase 3 测试） |
| **唯一 ID** | 每个任务 T01、T02…，全文档唯一 |
| **Description** | 这个任务做什么 |
| **Files** | 涉及哪些文件（路径） |
| **Verify** | 怎么验证这个任务完成 |
| **Depends** | 依赖哪些前置任务（T01 等） |
| **AC Covered** | 覆盖了 SPEC 的哪些 AC |
| **Coverage Matrix** | 末尾给一张 AC × Task 的覆盖矩阵，确保每条 AC 都有任务覆盖 |

### 格式要求
- 任务要**原子化**：一个任务一件事，能独立验证。
- **Coverage Matrix 必须完整**：每条 AC 至少被一个任务覆盖，不能有 AC 落空。

### 常见错误
- 任务粒度太大（"实现后端"）→ 无法独立验证 → 拆细。
- 缺 Coverage Matrix → 验收标准可能落空 → 必须补。

## 四、DIFF-ANALYSIS.md（代码逻辑差异分析）★ 模式 B 核心

### 目的
**基于当前 main 代码的真实状态**，说明要改哪里、为什么、有什么影响。这是接收方决定"怎么改代码"的关键输入，也是体现协作者价值的核心文档。

> SPEC/PLAN/TASKS 回答"要做什么"，DIFF-ANALYSIS 回答"当前是怎样的、要动哪里"。两者结合，接收方才能高效写代码。

### 必含 6 段

| 段落 | 内容 | 要点 |
|------|------|------|
| **1. 涉及功能与现状** | 需求涉及的功能，当前 main 怎么实现 | 必须引用**具体文件路径、函数名、数据流**，证明读过代码 |
| **2. 改动点清单** | 逐项列要新增/修改/删除什么 | 每项：`文件路径` + 改动说明 + 对应的 FR/Tasks 编号 |
| **3. 数据与接口影响** | 涉及的 DB 表、接口、数据流变化 | 标注是否动源数据库（**源 DB 只读，只能加新表/新库**） |
| **4. 影响面分析** | 改动波及哪些现有功能、上下游 | 会不会破坏现有逻辑？回归风险？ |
| **5. 风险与约束** | 技术风险 + 项目约束 | 端口规范、进程保护、SQLite 只读、DSML 过滤等已知坑 |
| **6. 不改什么** | 明确不在本次改动范围的代码 | 与 SPEC 的 Out of Scope 呼应 |

### 写作红线

| 红线 | 说明 |
|------|------|
| **必须引用真实代码** | 每个改动点都要有具体文件路径和函数，不能泛泛"修改后端逻辑" |
| **只分析不写代码** | 给改动方向和理由，不贴完整代码实现（那是接收方的事） |
| **诚实写风险** | 不确定的地方标注"需接收方确认"，不要装懂 |
| **尊重项目约束** | 源数据库只读、正式服端口禁碰、进程保护等红线必须遵守 |

### 质量自测
写完 DIFF-ANALYSIS，问自己：
- [ ] 接收方只看这份文档，能不能定位到每个要改的文件？
- [ ] 每个改动点是否都能追溯到 SPEC 的一条 FR？
- [ ] 有没有改动点没在 TASKS 里对应？（有就要补 TASKS 或删改动）
- [ ] 风险是否诚实？约束是否都提到了？

## 五、四份文档的一致性要求

一致性审核（Step 6）检查四份文档是否完全对齐：

```
SPEC 的每条 FR
   ↓ 必须有
PLAN 的技术方案
   ↓ 必须拆成
TASKS 的原子任务（Coverage Matrix 覆盖所有 AC）
   ↓ 每个任务必须有
DIFF-ANALYSIS 的具体改动点（文件路径）
```

**任何一环脱节，一致性审核都会 FAIL**。常见脱节：
- SPEC 有条 FR，但 TASKS 没有任务覆盖 → 补 TASKS。
- TASKS 有个任务，但 DIFF 找不到对应改动点 → 补 DIFF 或修正 TASKS。
- DIFF 提到改某文件，但不在任何 TASKS 范围内 → 删 DIFF 该项或加 TASKS。
- 四份文档对同一概念用了不同术语 → 统一术语。
