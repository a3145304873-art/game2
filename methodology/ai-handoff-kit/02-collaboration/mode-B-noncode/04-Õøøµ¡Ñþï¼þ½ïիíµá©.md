# 04 · 四步独立审核

> 受众：**协作者**。说明交付前的四步独立审核：每步审什么、谁来审、怎么算过、不过怎么办。
>
> 多数情况下这四步由 `/kickoff` **自动执行**，你只需理解机制、盯住通过标志。本文帮你搞懂"审得到底是什么"。

---

## 1. 为什么必须独立审核

**核心原则：审核 Agent 与写作过程上下文完全隔离，不是"自己审自己"。**

- 写 SPEC 的 AI 和审 SPEC 的 Agent 是**不同的独立实例**，审核 Agent 拿不到写作时的思考过程，只看到最终文档。
- 这避免了"作者滤镜"——写的人容易对自己的产出盲目自信。
- 协作者**不能跳过、不能代签**。审核 FAIL 就得改，改完重审，直到过或达到轮次上限。

> 项目历史教训（仓库根 CLAUDE.md 有载）：SQLite 数据被截断、React 闭包陷阱、JSON.parse 崩溃、SSE 双重序列化等 bug，都是独立审核能在"新鲜视角"下抓到、而作者自查漏掉的。

## 2. 四步审核总表

| 步骤 | 审核对象 | 执行 Agent | 通过标志 | 轮次上限 | 对应 checklist |
|------|---------|-----------|---------|---------|---------------|
| ① | `SPEC.md` | spec-reviewer | `.spec-passed` | 5 | [01-spec-review.md](../checklists/01-spec-review.md) |
| ② | `PLAN.md` | plan-reviewer | `.plan-passed` | 5 | [02-plan-review.md](../checklists/02-plan-review.md) |
| ③ | `TASKS.md` | tasks-reviewer | `.tasks-passed` | 5 | [03-tasks-review.md](../checklists/03-tasks-review.md) |
| ④ | SPEC+PLAN+TASKS（+DIFF）交叉一致 | consistency-reviewer | `.consistency-passed` | 2 | [04-consistency-review.md](../checklists/04-consistency-review.md) |

**当 `.consistency-passed` 出现 → 四步全部完成 → 立即停止，进入交付。**

---

## 3. 逐步详解

### ① SPEC 审核（spec-reviewer）

**审核什么**：SPEC.md 是否合格的技术规格书。
**核心关注**（详见 checklist）：
- FR 是否清晰、可实现、用 SHALL/SHALL NOT
- AC 是否可测试（GIVEN/WHEN/THEN）
- 是否有 Out of Scope
- FR 与 AC 是否一一覆盖
- 是否有臆测、模糊口号

**FAIL 常见原因**：FR 不可测、AC 缺失、范围不清。
**修复**：补全 AC、明确 FR、划清 Out of Scope，重审。

### ② PLAN 审核（plan-reviewer）

**审核什么**：PLAN.md 是否合格的技术实现计划。
**核心关注**：
- Key Decisions 是否给了 ≥2 备选方案及选定理由
- Technical Approach 是否可行、是否对齐 SPEC
- API Contracts 是否具体到字段
- Risks 是否识别充分

**FAIL 常见原因**：决策无备选（最常见）、方案脱离现状、接口契约模糊。
**修复**：补备选方案、对照 DIFF-ANALYSIS 修正方案、细化接口契约。

### ③ TASKS 审核（tasks-reviewer）

**审核什么**：TASKS.md 是否合格的任务分解（文档一致性维度）。
**核心关注**：
- 任务是否原子化（一事一任务、可独立验证）
- 每个 T 有 Description / Files / Verify / Depends / AC Covered
- Coverage Matrix 是否完整（每条 AC 有任务覆盖）
- 是否与 PLAN 对齐

**FAIL 常见原因**：任务粒度过大、缺 Coverage Matrix、AC 落空。
**修复**：拆细任务、补 Coverage Matrix、给落空的 AC 补任务。

### ④ 一致性审核（consistency-reviewer）★ 关卡

**审核什么**：SPEC ↔ PLAN ↔ TASKS ↔ DIFF-ANALYSIS **四份文档交叉一致**。
**核心关注**（四个维度）：
- **需求覆盖**：SPEC 每条 FR → PLAN 有方案 → TASKS 有任务 → DIFF 有改动点
- **无越界**：DIFF 提到的改动都在 TASKS 范围内，TASKS 任务都在 SPEC 范围内
- **术语一致**：四份文档对同一概念用相同术语
- **边界一致**：Out of Scope 四份文档说法一致

**FAIL 常见原因**：某条 FR 在 TASKS/DIFF 落空、DIFF 改动越界、术语不统一。
**修复**：定位是哪份文档漂移，修正后重审。
**注意**：一致性只有 **2 轮**上限，比前三步（5 轮）紧。更要在写作时就保持对齐，别指望审核时大改。

## 4. FAIL 怎么办

```
某步审核 FAIL
   │
   ├─ AI 自动读取审核报告，修正文档中的 CRITICAL 问题
   ├─ 自动重审（消耗 1 轮）
   │
   ├─ 循环直到 PASS ─────────────────────→ 写入 .xxx-passed，进入下一步
   │
   └─ 达到轮次上限仍 FAIL
         │
         └─ AI 停止，把剩余 CRITICAL 问题交给你
               │
               └─ 你的处理：
                   ├─ 能判断：指导 AI 如何修，继续
                   └─ 判断不了（可能是需求矛盾）：转交接收方裁决
```

**严重性分级**（审核报告里会标）：
- **CRITICAL**（阻塞）：必须修，否则不过。
- **WARNING**（应修）：建议修，影响质量。
- **INFO**（建议）：可选优化。

只有 **CRITICAL 清零**才算 PASS。

---

## 5. 轮次上限与升级

| 阶段 | 上限 | 达上限后 |
|------|------|---------|
| SPEC / PLAN / TASKS | 5 轮 | AI 停止，问题交协作者；协作者判断不了则升级接收方 |
| 一致性 | 2 轮 | 同上，但更紧迫（写作时就要对齐） |

**升级≠失败**。达到上限往往意味着"需求本身有矛盾"或"方向需要重新对齐"，这正是需要接收方介入的信号。把审核报告（`reviews/` 下）连同问题一起发给接收方。

---

## 6. 协作者的审核纪律

| 要 | 不要 |
|----|------|
| 让 AI 跑完整四步审核 | 手动跳过某步 |
| 盯住每步的 marker（.spec-passed 等） | 在审核 FAIL 时硬过 |
| 达上限时把问题升级给接收方 | 自己拍脑袋代替审核判断 |
| 理解每步审什么（本文 + checklist） | 把审核当走过场 |

---

## 7. 关于"对齐审核"（不在你的四步内）

**对齐审核（alignment）由接收方做，不是协作者的四步之一。**

- 你交付后，接收方会用 alignment-reviewer 判断"这批文档整体是否忠实于原始需求意图"。
- 你**不需要**做对齐审核——这是接收方作为"最终把关者"的职责。
- 但你在写作时要**始终以 ISSUE.md 为北极星**，确保产出服务于原始需求。这相当于"前置对齐"，能让接收方的对齐审核更顺利。
