# 05 · 对齐审核清单（接收方专用）

> **审核对象**：协作者交付的整批文档（REQUIREMENTS + SPEC + PLAN + TASKS + DIFF-ANALYSIS）
> **执行者**：**接收方（项目负责人）**——这是接收方的专属职责，**不属于协作者的四步审核**。
> **工具**：alignment-reviewer（独立 Agent）；或接收方人工对照本清单。
> **判断**：产出是否**忠实于原始需求意图**。
> **结果**：PASS → Spec 验收；FAIL → 小修 / REDO（见 [05-交付与对齐验收.md](../mode-B-noncode/05-交付与对齐验收.md)）。

---

## 为什么接收方要做对齐审核

协作者的四步审核保证的是**文档质量**（格式、覆盖、一致性）；对齐审核保证的是**方向正确**（这批文档真的解决了 ISSUE 提出的真实问题吗）。

质量过关 ≠ 方向正确。一份格式完美但跑题的 SPEC，四步审核可能放行，但对齐审核必须拦下。**方向把关只能由掌握需求全貌的接收方做**。

---

## 审核维度

### A. 意图忠实（CRITICAL · 核心）
- [ ] 产出解决的是 ISSUE.md 提出的**真实问题**，而非协作者理解的"近似问题"
- [ ] 没有跑题、自嗨、过度发挥
- [ ] 核心目标（ISSUE 的 Goals）都被产出覆盖
- [ ] 验收标准（AC）是接收方**真正想要的验收点**，而非协作者自行设定的

### B. 范围一致（CRITICAL）
- [ ] 做的是 ISSUE 要的范围，无擅自扩大（镀金）
- [ ] 无擅自缩小（把 ISSUE 要的某部分悄悄放进 Out of Scope）
- [ ] Out of Scope 的取舍接收方认可（确实不该做）

### C. 假设合理（CRITICAL）
- [ ] REQUIREMENTS.md 中的假设（尤其 `[auto-decided]`）成立
- [ ] 协作者在澄清环节的判断接收方认可
- [ ] 无"基于错误假设推导出的整套方案"

### D. 可落地（CRITICAL）
- [ ] 接收方基于这批文档能**顺畅写代码**，无悬空、无矛盾
- [ ] PLAN 的技术方案接收方认可且可实现
- [ ] TASKS 的任务划分接收方接受
- [ ] DIFF-ANALYSIS 的改动方向接收方确认无误

### E. DIFF 可信（CRITICAL）
- [ ] DIFF-ANALYSIS 引用的文件路径、函数名**真实存在于 main**（抽查核对）
- [ ] 现状描述与 main 代码实际一致（不是 AI 编造）
- [ ] 改动点合理，没有"幻觉式改动"（改了不存在的代码）

### F. 价值与风险（WARNING）
- [ ] 产出的商业价值与 ISSUE 预期一致
- [ ] 风险识别充分，未隐瞒
- [ ] 需接收方确认的点（DIFF 5.3 节）已明确列出，可决策

---

## 审核动作（接收方操作建议）

1. **重读 ISSUE.md**，回忆原始需求意图（这是北极星）。
2. **抽查 DIFF-ANALYSIS 的代码引用**：随机挑 2-3 个改动点，打开 main 代码核对路径/函数是否真实、现状描述是否准确。这一步能快速识破"AI 编造"。
3. **核对范围**：ISSUE 的 In Scope 是否都在产出中？Out of Scope 是否合理？
4. **判断可落地性**：设想自己要开始写代码，看文档够不够、顺不顺。
5. 用 alignment-reviewer 跑一遍（输入 ISSUE + 全部交付文档），对比自己的判断。

---

## 审核结论与处理

| 结论 | 处理 |
|------|------|
| **PASS**（意图忠实、范围一致、可落地） | 进入 Spec 验收（[05-交付与对齐验收.md](../mode-B-noncode/05-交付与对齐验收.md) 第 5 步） |
| **小修**（个别点偏差） | 让协作者按本清单意见修订，重走一致性审核后重新交付 |
| **FAIL - 方向跑偏** | 接收方重新澄清需求，协作者走 `/kickoff` REDO（备份原产出 → 清 marker → 重跑 Phase 1-4） |
| **FAIL - DIFF 不可信**（大量幻觉） | 协作者重做 Issue 分析 + DIFF，要求严格引用真实代码 |

---

## 对齐审核 vs 四步独立审核（区别）

| 维度 | 四步独立审核（协作者） | 对齐审核（接收方） |
|------|---------------------|------------------|
| 谁做 | 独立 AI Agent | 接收方（人 + alignment-reviewer） |
| 审什么 | 文档质量（格式/覆盖/一致性） | 方向正确（是否忠实需求意图） |
| 基线 | 文档规范 / checklist | **原始 ISSUE.md**（北极星） |
| 通过标志 | `.spec/plan/tasks/consistency-passed` | 接收方签字（spec status: accepted） |
| 性质 | 自动化质量门 | 人工方向把关 |

> 两者互补，缺一不可。四步审核放行质量合格但可能跑题的文档；对齐审核拦下跑题。模式 B 的质量保障 = 四步审核 + 对齐审核。
