# 多人协同交付规范

> **版本**: v1.0.0 | **生效日期**: 2026-06-22 | **维护人**: N8872（接收方 / 项目负责人）
>
> 本规范定义本项目（AI 文案助手）的多人协同交付方式。面向两类协作者：**写代码的开发同学**与**只交付文档的合作同学**。

---

## 1. 这套规范解决什么问题

本项目由项目负责人（以下简称**接收方**）主导开发。当不断有新增功能需求时，单线开发会成为瓶颈。本规范把"一个新增需求从提出到落地"拆成可分工、可交接、可审核的标准化流程，让其他同学能安全地参与。

核心矛盾是：**不是所有协作者都写代码**。所以本规范区分两种协同模式，分别给出流程。

---

## 2. 两种协同模式速查

| 维度 | 模式 A：开发者模式 | 模式 B：非代码交付模式 |
|------|--------------------|------------------------|
| **适用对象** | 会写代码、能跑通项目的开发同学 | 不写代码、只交付需求分析文档的合作同学（产品/运营/其他部门） |
| **协作者产出** | 可运行的分支代码（含测试） | 三类标准化文档（SPEC + Task Plan + 代码差异分析） |
| **协作者工具** | Claude Code（直接在本仓库分支开发） | Claude Code（跑 `/kickoff` 规划流程，不写业务代码） |
| **接收方工作** | Code Review + QA + 合并主干 | 对齐审核 + Spec 验收 + 基于验收 Spec 做代码开发 |
| **流程终点** | 代码合并进 `main`，打 tag 发版 | 交付合格文档，由接收方接手代码实现 |
| **详细文档** | [mode-A-developer.md](./mode-A-developer.md) | [mode-B-noncode/](./mode-B-noncode/) |

> **如何选模式**：协作者能跑通项目、能提交可运行代码 → 模式 A；协作者只负责把需求想清楚、把方案写明白 → 模式 B。两种模式的边界由接收方在派发需求时明确指定。

## 3. 角色与职责分工

| 角色 | 谁 | 职责 |
|------|----|------|
| **接收方** | N8872（项目负责人） | 派发需求、提供最新 main 源码、提供本规范、做最终对齐审核与 Spec 验收、接手代码开发与发版 |
| **协作者** | 开发同学 / 合作同学 | 按指定模式完成交付；模式 A 写代码，模式 B 写文档；自行完成交付前的独立审核 |
| **AI Agent** | Claude Code | 辅助协作者分析需求、对比代码、产出文档、执行独立审核 |

**关键边界（务必记住）**：
- **接收方负责"对齐审核"**——即判断协作者的产出是否忠实服务于原始需求意图。这一步**永远由接收方做**，不交给协作者。
- **协作者负责"交付前的独立审核"**——即对自己的产出做质量把关。模式 B 下为四步独立审核（见下）。
- 协作者的审核用 AI Agent 独立完成，但**审核 Agent 的上下文与产出过程隔离**（不能"自己审自己写的"），由 `/kickoff` 自动保证。

## 5. 模式 B 端到端流程（重点）

模式 B 是本规范的核心。完整链路如下（左为接收方，右为协作者）：

```
[接收方]                                          [协作者]
   │
   ├─ ① 同步最新 main 源码给协作者
   ├─ ② 提供本 collaboration/ 规范
   ├─ ③ 写需求 Issue（要做什么、为什么、期望）
   │ ─────────────────────────────────────────→
   │                                                ├─ ④ 启动 Claude Code，通读本规范
   │                                                ├─ ⑤ 与 AI 几轮交互，把需求说清楚
   │                                                ├─ ⑥ AI 做 Issue 分析：对比当前 main
   │                                                │     代码实现，定位差异与改动点
   │                                                ├─ ⑦ 跑 /kickoff 产出 SPEC → PLAN → TASKS
   │                                                ├─ ⑧ 产出《代码逻辑差异分析》文档
   │                                                ├─ ⑨ 四步独立审核（全 PASS）：
   │                                                │     SPEC审 → PLAN审 → TASKS审 → 一致性审
   │                                                └─ ⑩ 按交付清单自检，打包交付
   │ ←─────────────────────────────────────────
   ├─ ⑪ 对齐审核（整体是否符合需求意图）  ← 非代码交付到此结束
   ├─ ⑫ 最终 Spec 验收（签字确认）
   └─ ⑬ 接收方基于验收 Spec 做代码开发、发版
```

**协作者的流程终点 = 步骤 ⑩**。步骤 ⑪⑫⑬ 是接收方的工作。

> 协作者使用的 `/kickoff` 命令本身有更多阶段（readiness、alignment、implement、QA、merge），但**模式 B 只跑到「一致性审核」（Phase 4）即停**——后续阶段由接收方接手。详见 [mode-B-noncode/02-协作者操作流程.md](./mode-B-noncode/02-协作者操作流程.md)。

## 6. 快速开始

> **首次使用？先读这两份**：[环境准备.md](./环境准备.md)（装 Claude Code + Harness）→ [快速开始.md](./快速开始.md)（5 步上手）。

### 如果你是协作者

1. 先读 [mode-B-noncode/README.md](./mode-B-noncode/README.md)（非代码交付）或 [mode-A-developer.md](./mode-A-developer.md)（开发者）。
2. 确认接收方派给你的模式和需求 Issue。
3. 按对应模式的"操作流程"逐步执行。
4. 交付前对照 [templates/DELIVERABLE-CHECKLIST.template.md](./templates/DELIVERABLE-CHECKLIST.template.md) 自检。

### 如果你是接收方

1. 派发需求前，按 [mode-B-noncode/01-接收方准备.md](./mode-B-noncode/01-接收方准备.md) 准备好源码、规范、Issue。
2. 收到交付后，按 [mode-B-noncode/05-交付与对齐验收.md](./mode-B-noncode/05-交付与对齐验收.md) 做对齐审核与验收。
3. 验收通过，进入代码开发。

## 7. 术语约定

| 术语 | 含义 |
|------|------|
| **接收方** | 项目负责人 N8872，需求的最终把关者与代码实现者 |
| **协作者** | 承接需求的同学（开发或合作部门） |
| **main** | 主干分支，正式服代码（后端 3500 / 前端 8500） |
| **SPEC** | 技术规格书，描述"做什么、做到什么程度" |
| **PLAN** | 技术实现计划，描述"技术上怎么做" |
| **TASKS** | 任务分解，把 PLAN 拆成可执行的原子任务 |
| **Task Plan** | PLAN 与 TASKS 的合称（协作者交付物之一） |
| **差异分析** | 《代码逻辑差异分析》，对比当前 main 代码、说明要改哪些地方（不写代码） |
| **对齐审核** | 接收方判断"产出是否忠实于原始需求意图" |
