# Plan Quality Checklist

> Plan 审核员使用此清单逐项检查 plan.md 质量。

## CRITICAL (必须通过)

### 结构完整性
- [ ] Plan 包含「Technical Approach」段落，说明技术方案和选型理由
- [ ] Plan 包含「Key Decisions」决策表，每个决策有备选方案和理由
- [ ] Plan 包含「Risks & Mitigations」风险表，有概率/影响/缓解措施
- [ ] Plan 包含「Testing Strategy」测试策略，说明测试类型和范围
- [ ] Plan 包含「Dependencies」依赖项列表

### SPEC 覆盖率
- [ ] 每个 FR-XX 在 Plan 中有对应的技术方案描述
- [ ] 技术方案描述具体（不是"使用合适的技术"）
- [ ] 数据变更（如有）有字段级描述
- [ ] API 变更（如有）有请求/响应格式说明

### 决策质量
- [ ] 每个关键决策列出了至少 2 个备选方案
- [ ] 选择理由具体且与技术/业务约束相关
- [ ] 没有遗漏明显的重大技术选型

### 风险评估
- [ ] 风险描述具体（不是"可能会出问题"）
- [ ] 缓解措施可操作（有具体步骤，不是"小心处理"）
- [ ] 概率和影响评估合理

### 颗粒度与拆分（防止实现期 silent defer）
- [ ] **PLAN 中任何描述为可执行单元的步骤（plan-level task）若满足以下任一条件，必须拆分为多个独立步骤，或为每个子步骤列出独立的 Verify 断言：**
  - 包含 4 个及以上子步骤（"先做 A，再做 B，然后 C，最后 D"）
  - 跨越 3 个及以上文件或模块
  - 影响范围覆盖 2 个及以上不相交 FR
- [ ] 不存在「一个 plan 步骤同时实现多个 FR」的合并描述（合并会导致后续 defer 一个 FR 时无法精确定位）

### 决策与覆盖状态一致性（Key Decisions 反映 defer）
- [ ] **Key Decisions (KD) 中任何条目若提及 defer / split / follow-up / 后续 spec / Phase N+ / out of scope，必须在 PLAN 内显式：**
  - 更新对应 FR-XX 的覆盖状态（标记为 `Partial` / `Deferred`）
  - 指向一个 follow-up spec 占位（即使只是 "TBD-XX"）
- [ ] KD 的「选择理由」段落不得隐含 defer — 若选某方案是因为「另一个方案太复杂留到以后」，必须显式记录为 defer 决策，不能伪装成纯技术选型。

## WARNING (应当通过)

### 非功能需求
- [ ] 性能要求在 Plan 中有对应措施（如需要）
- [ ] 安全考虑在 Plan 中有对应措施（如涉及）
- [ ] 兼容性要求已考虑（如涉及）

### 测试策略
- [ ] 每个 AC 有对应的测试类型（Unit/Integration/E2E）
- [ ] 关键用户旅程有 E2E 测试计划
- [ ] 边界条件和异常场景有测试覆盖

### 可维护性
- [ ] Plan 中没有硬编码的值（端口、URL、密钥等）
- [ ] 新增依赖有版本说明和选型理由
- [ ] 配置项有说明（环境变量、配置文件）

## INFO (建议)

### 文档质量
- [ ] 技术术语使用准确
- [ ] 段落结构清晰，易于阅读
- [ ] 与 spec.md 的术语一致
- [ ] 无拼写错误

---

## 对抗式审核规则（Adversarial Mindset）

> 审核员必须以「找问题」而非「确认无误」的心态工作。

- [ ] **若报告 0 CRITICAL + 0 WARNING，必须给出显式的「为何无问题」论证段落。**
  - 论证必须引用具体证据（file:line / PLAN 章节 / FR 编号 / 代码模式），不能是空泛的「看起来没问题」。
  - 一份「0 CRITICAL + 0 WARNING 且无论证段」的报告视为 **INVALID**，等同于 FAIL。
- [ ] 审核员主动尝试至少一次「证伪」：假设 PLAN 有问题（如某个 task 在实现期会爆），反推会在哪里暴露，并检查该假设是否被现有文档排除。
- [ ] 报告至少列出 1 条「最弱项」（最接近 WARNING 但未达阈值的薄弱点），即使最终未升级为 WARNING。
