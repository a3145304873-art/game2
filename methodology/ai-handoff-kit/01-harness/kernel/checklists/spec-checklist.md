# Spec Quality Checklist

> Spec 审核员使用此清单逐项检查 SPEC.md 质量。

## CRITICAL (必须通过)

### 完整性
- [ ] Spec 包含「背景与动机」段落，清晰说明为什么要做这个变更
- [ ] Spec 包含「详细需求」段落，每个需求具体且可衡量
- [ ] Spec 包含「验收标准」段落，每个标准带唯一 ID（AC-01, AC-02...）
- [ ] Spec 包含「范围边界」段落，明确说明不包含什么
- [ ] 所有验收标准都是可独立测试的（不能有"等等"、"类似"等模糊词）

### 可行性
- [ ] 技术方案无自相矛盾
- [ ] 依赖项已明确列出
- [ ] 假设条件已声明
- [ ] 不存在明显的技术障碍

### 边界条件
- [ ] 错误状态已覆盖（输入验证失败、网络错误、权限不足等）
- [ ] 边界值已考虑（空值、最大长度、并发情况）
- [ ] 失败模式已记录

### 颗粒度控制（防止 silent defer 的根因）
- [ ] **不存在「大颗粒 FR」**：任何 FR-XX 若同时满足以下两条，必须在 spec 阶段拆分为多个独立 FR-XX，或在 PLAN.md 中强制 split：
  - 包含 4 个及以上子步骤（隐含的 "and then" 序列），或
  - 影响范围横跨 2 个及以上不相交功能区域（如 "登录" + "权限" + "审计日志" 混在一个 FR）
- [ ] 每个 FR 都能被一个独立 task 原子地覆盖（不存在 "半个 FR" 需要跨 task 拼接才能验证的情况）
- [ ] FR 之间无隐含的时序耦合（即 FR-02 不应隐含要求 FR-01 先完成才能定义清楚）

## WARNING (应当通过)

### 可测试性
- [ ] 每个验收标准都有明确的验证方法（手动/自动/API/视觉）
- [ ] 验收标准的预期结果具体（不是"正常工作"，而是"返回 200 + JSON 包含 id 字段"）
- [ ] UI 变更有交互描述（点击什么、看到什么、预期结果）

### 范围控制
- [ ] 单个 Spec 不超过 8 个验收标准（超出应拆分）
- [ ] 没有隐含的额外需求（藏在描述中但未列为 AC）
- [ ] 没有与当前需求无关的"顺便"改动

### 非功能需求
- [ ] 性能要求已说明（如需要）
- [ ] 安全考虑已说明（如涉及用户输入、权限）
- [ ] 数据变更已描述字段级别细节（如涉及数据库）

## INFO (建议)

### 文档质量
- [ ] 无拼写错误
- [ ] 技术术语使用准确
- [ ] 段落结构清晰，易于阅读
- [ ] 代码示例（如有）语法正确

---

## 对抗式审核规则（Adversarial Mindset）

> 审核员必须以「找问题」而非「确认无误」的心态工作。

- [ ] **若报告 0 CRITICAL + 0 WARNING，必须给出显式的「为何无问题」论证段落。**
  - 论证必须引用具体证据（file:line / SPEC 章节号 / AC 编号 / 代码模式），不能是空泛的「看起来没问题」。
  - 一份「0 CRITICAL + 0 WARNING 且无论证段」的报告视为 **INVALID**，等同于 FAIL。
- [ ] 审核员主动尝试至少一次「证伪」：假设 SPEC 有问题，反推会在哪里暴露（实现期 / QA 期 / 上线后），并检查该假设是否被现有文档排除。
- [ ] 报告至少列出 1 条「最弱项」（最接近 WARNING 但未达阈值的薄弱点），即使最终未升级为 WARNING。
