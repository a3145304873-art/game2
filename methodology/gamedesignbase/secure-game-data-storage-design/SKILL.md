# 安全游戏数据存储设计

## 适用场景

- 设计在线游戏的玩家数据存储架构
- 评估现有游戏的数据存储安全风险
- 制定反作弊机制和数据完整性保护方案
- 决定特定数据字段的存储位置（客户端 vs 服务器端）
- 移动端游戏的数据安全风险评估

## 核心原则：客户端不可信

**必须假设所有客户端数据都可能被篡改**。任何存储在玩家设备上的数据都面临被修改以获取不公平优势的风险。加密不能解决此问题，只能增加篡改难度。

## 数据分类判定

将玩家数据明确区分为两类：

### 类型A：设置与偏好数据（可本地存储）
- **特征**：影响外观和玩法方式，但不影响游戏状态
- **示例**：角色装饰（帽子、鞋子、车辆皮肤）、界面设置、音效偏好
- **存储位置**：允许客户端本地存储
- **判断标准**：修改此数据不会给玩家带来游戏内的竞争优势或经济收益

### 类型B：游戏状态数据（必须服务器存储）
- **特征**：与游戏状态实际相关，直接影响玩家竞争地位
- **示例**：
  - 位置坐标与地图进度
  - 得分、排名、成就状态
  - 属性值（攻击力、防御力、等级）
  - 虚拟货币与物品数量
  - 职业、技能、装备属性
- **存储位置**：**绝对禁止客户端存储**，必须服务器端持久化
- **判断标准**：修改此数据会直接改变玩家在游戏中的状态或经济地位

## 存储位置决策流程

```
数据类型判定
    │
    ├─→ 设置/偏好类（外观、配置）
    │       └─→ 允许本地存储
    │
    └─→ 游戏状态类（金钱、属性、进度）
            └─→ 强制服务器存储
                    ├─→ 退出游戏：服务器端完整性检查
                    └─→ 登录游戏：与服务器备份比对验证
```

**关键约束**：
- 即使使用强密码技术加密，类型B数据也**不得**存储在客户端
- 网络连接是访问敏感数据的必要条件
- 对每个角色产生的大量敏感数据必须全部服务器端管理

## 服务器端实施方案

### 1. 数据退出检查机制
当玩家退出游戏时：
- 在服务器端执行数据完整性检查
- 验证关键数值是否在合理范围内
- 记录当前状态快照作为基准

### 2. 登录验证机制
当玩家重新登录时：
- 从服务器加载权威数据状态
- 比对客户端上报数据（如有）与服务器备份
- 检测期间是否存在异常修改
- 发现不一致时，以服务器数据为准并记录异常

### 3. 数据同步策略
- 敏感数据操作必须实时服务器验证
- 避免客户端预计算后提交结果（如战斗结果、掉落计算）
- 关键操作（交易、升级）需服务器端重新计算确认

## 移动端特殊风险评估

### 当前风险认知（误区）
- **现状**：许多手机游戏将敏感数据存储在设备本地
- **理由**：目前手机破解率较低，玩家普遍缺乏技术能力修改本地数据

### 风险预警（必须考虑）
- **趋势**：手机破解工具和教程正在快速普及
- **建议**：
  - 即使是手机游戏，也应遵循服务器端存储原则
  - 如必须本地存储（离线模式），实施严格的本地加密和校验机制
  - 准备从本地存储向服务器存储迁移的技术方案

## 实施检查清单

- [ ] 已列出所有玩家数据字段并分类为类型A或类型B

- [ ] 客户端仅存储类型A数据（设置、外观配置）
- [ ] 实现了退出时的服务器端数据完整性检查
- [ ] 实现了登录时的数据一致性验证
- [ ] 移动端游戏已评估未来破解风险并制定应对计划

## 常见错误

1. **依赖客户端加密**：认为加密本地存储文件即可防止篡改（错误：客户端密钥可被提取）
2. **混合存储逻辑**：将金钱存储在服务器但将物品属性存储在客户端（导致属性修改漏洞）
3. **信任客户端计算**：接受客户端提交的战斗结果而不在服务器端重新验证随机数和伤害公式
4. **忽视离线模式风险**：为支持离线游戏将关键数据本地存储，上线后未进行充分的数据冲突检测

## 示例：大富翁类游戏数据分类

**类型A（可本地）**：
- 玩家选择的棋子外观（汽车、帽子、鞋子样式）
- 棋盘主题偏好
- 音效和音乐音量设置

**类型B（必须服务器）**：
- 玩家在棋盘上的当前位置
- 持有的现金数量和不动产清单
- 房屋和酒店建设状态
- 当前回合数和游戏进度
