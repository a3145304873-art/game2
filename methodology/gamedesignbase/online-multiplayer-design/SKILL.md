# 在线多人游戏设计

## 使用时机
- 设计在线游戏（非单人游戏）
- 存在玩家社交互动系统
- 设计永恒世界类游戏
- 游戏需要支持玩家不同时在线
- 需要降低玩家同时登录门槛
- 希望通过社交网络传播
- 游戏包含需要等待的回复机制
- 游戏为实时同步多人模式

## 在线游戏设计师的角色扩展

### 角色双重性认知

#### 基础角色
- 游戏设计者（Game Designer）——设计核心游戏机制

#### 扩展角色
- 建筑师（Architect）——设计社会互动空间与系统
- 关键论断：这"实际上对你来说是最苛刻的挑战，这远比单人游戏中的核心机制要难得多"

### 建筑师角色的具体内涵

#### 社会情境培育皿（Petri Dish）构建者
- 在线游戏会成为"整个成长的社会情境的培养皿"
- 设计师需为不可预测的社会演化提供基础设施和规则框架

#### 不可预测性管理
- 核心挑战："你几乎不可能预测到它以后的成长会发生什么"
- 应对策略：设计弹性系统，支持 emergent gameplay（涌现式玩法）

### 设计优先级调整

#### 传统单人游戏
- 核心机制（Core Mechanics）为最高设计重点

#### 在线游戏
- 社会架构（Social Architecture）与核心机制并重
- 前者难度更高

### 社交系统技术实现（已知有效手段）

1. 文字消息系统（最基础）
2. 语音交流系统（广泛应用）
3. 视频系统（宽带普及后可行）
   - 未来趋势：玩家穿着适合游戏角色的衣服在摄像机中展示

### 延伸阅读建议

- 推荐书籍：《Community Building on the Web: Secret Strategies for Successful Online Communities》
- 作者：Amy Jo Kim
- 出版年份：2000年
- 评价标准："更加卓越和更有深刻见解"

## 玩家角色设计原则：丰富性与可转换性

### 角色丰富性设计原则

#### 核心前提
- 在永恒世界中，玩家不跟随单一故事线
- 理论上可从许多不同的事情中做选择
- 因此有更多机会定义自己的角色

#### 历史演进标准
- 早期永恒世界仅提供少量角色
- 现代游戏必须做到「更丰富、更多样化」

#### 失败预警机制
- 「如果在你的游戏中能够做的事情太少，它将面临失败」
- 这是强制性设计约束

#### 内容丰富性要求
- 必须提供「不同的方式来玩游戏」
- 必须提供「不同的方式去体验整个世界」
- 即使是最酷的游戏机制，在一段时间后也会变得无聊，必须通过多样性对抗疲劳

#### 竞争防御策略
- 玩家会转移到另一个他们能够得到新体验的世界中去
- 因此必须持续给游戏增加内容
- 或者「最好是在现在世界的基础上增加子世界」

### 角色可转换性设计原则

#### 分类义务
- 作为设计师，必须对玩家可能想要扮演的角色进行分类
- 使这些游戏角色对游戏世界更加有意义

#### 转换自由保障
- 当玩家认为自己更合适另一个角色时，必须给玩家转换角色的自由

#### 转换难度控制
- 转换「通常并不容易或者立刻生效」——设置合理门槛但保留可能性

#### 持续世界适配
- 因为世界持续不断地运转，并没有故事的结局
- 不能期望玩家永远都使用同样的方式玩游戏

#### 现实类比依据
- 「就像人们随着时间流逝会更换职业和兴趣一样，玩家也需要能够转换角色」

## 非同步游戏设计框架与机制

### 核心定义确认

#### 确立非同步性质
- 玩家行动不需要同步进行
- 不需要同时登录游戏
- 不必等待其他玩家回合（尽管玩家可以选择等待，或发现这样容易与其他玩家联合）

#### 分类定位
- 与永恒世界等大型非同步游戏区分（除非玩家为共同追求同时登录）
- 应作为独立类别处理，区别于传统同步在线游戏

### 社会网络集成与传播机制

#### 平台选择
- 通过社会媒体网络（如脸书）进行操作

#### 病毒式传播设计
- 设置游戏内奖励，明确促使玩家邀请朋友加入游戏

#### 参考案例：《开心农场》模式
- 本质为单人游戏
- 每个玩家按自己速度向目标努力
- 但通过联合其他玩家共享虚拟资源可成长更快、更成功

### 游戏模式选择策略（关键决策点）

#### 首选模式
- 单人联合模式（Single-player cooperative）——允许玩家独立进度，但提供共享资源加速机制

#### 可选模式
- 多人联合模式（Multiplayer cooperative）
- 基于团队模式（Team-based）

#### 明确避免
- 多人竞争模式（Multiplayer competitive），仅在比较最高分的限制事件中例外使用

#### 术语定义
- 此类模式可称为"单人联合游戏"，区别于传统游戏形式

### 团队目标与公平性架构

#### 贡献机制
- 在联合游戏与基于团队游戏的事件中，确保每个玩家都能为团队目标做出贡献

#### 独立性原则
- 为了公平，特别是考虑到非同步性质，玩家之间的目标必须设计为相互独立

#### 规模优势
- 此机制在大型团队中运行良好
- 可避免过多依赖玩家个人能力
- 适应不同水平玩家混合的团队

### 玩家流动与联合管理

#### 加入/离开优化
- 利用非同步性质消除玩家加入和离开游戏的问题
- 游戏本身不需要玩家在特定时间内登录

#### 联合策略调整
- 减少玩家之间联合（collusion）的管控需求
- 因游戏通常为合作性质，设计应更多鼓励团队合作而非禁止联合

### 技术与社会设计平衡

- 非同步特性既是技术架构特征，也是社会互动设计基础
- 通过消除时间同步约束，扩大潜在玩家基数，降低参与门槛

## 多人游戏耗时活动设计约束与反模式

### 核心约束识别

- 由于多人游戏禁止个体时间跳跃和加速，玩家无法通过游戏机制跳过等待时间
- 玩家不能在等待时下线然后在结束后登录
- 玩家不能切换到计算机的其他程序（alt-tab）来打发时间
- 任何强制等待都会迫使玩家盯着屏幕无事可做

### 负面案例分析（《无尽的任务》冥想机制）

#### 机制描述
- 使用"冥想"机制，玩家必须简单地等待一段时间来回复魔力

#### 设计缺陷详细分析
- 没有加速这个过程的办法——它确实包含了等待（实时等待）
- 玩家不能在冥想的时候下线，然后在冥想结束后登录
- 玩家甚至不能切换到计算机的其他程序中

#### 补救措施评估
- 设计师Verant Interactive最终创建了一个小游戏作为玩家等待时的消遣
- 但这并不是一个治本的方法，只是缓解症状

### 设计决策流程

#### 检查点1：评估该耗时活动本身是否吸引玩家？
- 如果是：可以继续使用，但需监控玩家反馈
- 如果否（如纯被动等待）：进入检查点2

#### 检查点2：是否可以通过机制重构消除强制等待？
- 优先考虑重新设计核心机制（如将被动回复改为主动操作回复）
- 次选：允许离线进度或后台进度
- 避免：仅仅添加消遣性小游戏作为"止痛片"

### 关键设计原则

- 绝对避免"不能吸引玩家的无聊特征"
- 如果必须存在等待，确保等待期间玩家可以进行其他有意义的游戏活动（如交易、社交、探索）
- 绝不允许强制玩家处于"锁屏等待"状态（除非这是经过精心设计的、有趣的核心玩法）

## 关键变量

| 变量名 | 类型 | 描述 |
|--------|------|------|
| designer_role | string | 设计师当前认知角色：游戏设计者/建筑师 |
| social_system_type | string | 社交系统类型：文字/语音/视频 |
| prediction_difficulty | enum | 社会演化可预测性：几乎不可预测 |
| network_bandwidth | string | 网络带宽条件：窄带/宽带 |
| role_diversity_index | qualitative | 评估游戏提供的不同玩法和体验方式的数量级 |
| content_update_frequency | temporal | 新增内容或子世界的节奏，用于对抗玩家疲劳 |
| role_transition_cost | difficulty_scale | 玩家切换角色所需付出的时间/资源成本，应设置为'不容易'但可行 |
| login_sync_requirement | boolean | 是否需要玩家同时在线 |
| game_mode_type | enum | 游戏模式类型：单人联合/多人联合/团队/竞争 |
| goal_independence | boolean | 玩家目标是否相互独立 |
| social_reward_mechanism | object | 邀请好友的奖励配置 |
| waiting_duration | duration | 玩家需要等待的实际时间长度 |
| player_engagement_level | enum | 等待期间玩家的参与程度：主动参与/被动观察/完全闲置 |
| alternative_activity_availability | boolean | 等待期间是否可执行其他游戏操作 |

## 输出结果

设计师应采取的行动：
1. 学习社会架构设计
2. 研究社区建设策略
3. 为不可预测性设计弹性系统
4. 根据带宽条件选择社交技术方案

输出为游戏设计的决策依据：
1. 检查当前角色系统丰富度是否达标
2. 规划内容扩展路线图
3. 设计角色转换机制的具体实现方案

完整的非同步游戏设计方案，包含：
- 非同步交互架构
- 社会网络集成点
- 合作导向的游戏模式选择
- 独立目标团队系统
- 玩家流动管理策略

输出设计决策：
- 若存在强制无聊等待，则标记为"需要重新设计"
- 若已提供 engaging 的并行活动，则标记为"可接受但需监控"
