# 游戏类型与核心机制设计

## 使用时机
- 计划创建跨越现有类型的游戏
- 考虑组合不同游戏功能
- 开始设计游戏核心机制
- 需要确定时间推进方式
- 需要编写核心机制文档供程序员实现

## 混合类型游戏设计

### 混合类型定义与结构

**定义**
- 跨越类型，将不同功能组合在一起以至于很难进行分类的游戏

**结构模式A（主从模式）**
- 在一种类型中提供"主要游戏模式"
- 在另一种类型中提供"一个或多个迷你游戏模式"

**结构模式B（融合模式）**
- 混合通常不会一起呈现的挑战
- 创造真正的新类型

### 成功案例分析

**案例1（动作+冒险）**
- 最新的《塞尔达传说》（Legend of Zelda）是最成功的混合体
- 早期2D版几乎完全是动作游戏
- 新版中"占主要作用的仍是动作"，但"通常也会包括一个故事和解谜"
- 引入冒险游戏元素

**案例2（RPG+益智）**
- 《益智之迷》（Puzzle Quest）是成功混合体
- 本身是"简单的角色扮演游戏"
- 使用"三消这个用于许多休闲游戏的模式来实施战斗"

### 风险评估与缓解

**开发风险**
- "交叉类型会让设计和开发团队增加更多工作，同时风险也会增大"

**市场风险**
- "虽然混合类型可能会吸引到两类玩家群体，但也有可能最终两类人都吸引不了"

**受众风险**
- "许多玩家（和游戏评论者）喜欢特定的类型，并且不想面对他们通常避免的某种挑战"

**缓解措施**
- "如果你打算做一些不寻常的改变，一定要早点与代表你目标受众的人一起检测你的想法"

### 真实性原则（核心设计伦理）

**创造力保护**
- "不应该让标准类型限制住你的创造力——特别是在概念阶段"

**全新类型处理**
- "如果你有一个全新的、从未见过的类型游戏想法，要记得设计它，如你所想；不要试图把它钉入它不属于的类型"

**真实性要求**
- "游戏需要本身是真实的，所以真正的混合游戏可能需要混合通常不会一起呈现的挑战"

**禁止性规定**
- "但是没有好的理由，不要混合不同类型的特征；一个游戏应该跨越流派，此时它才真正需要作为游戏的一部分"

**反例警示**
- 一个飞行模拟器与逻辑拼图插入在游戏的中间，只是为了使游戏不同于其他飞行模拟器
- 这只会惹恼飞行模拟迷
- 这种为了差异化而强行插入无关类型特征的做法必须避免

## 实时游戏与回合制游戏核心机制设计

### 第一步：判断游戏时间系统类型

**实时游戏**
- 世界持续运转，不依赖玩家输入

**回合制游戏**
- 核心机制在玩家回合间可能闲置或仅处理AI

### 第二步：实时游戏核心机制设计要点

1. 核心机制指定生命世界的各种参数，这个世界不管玩家是否做出了行动，都按照自己的方式运转
2. 设计的机制应是一个过程，这个过程持续地运转或者在延长期内运转
3. 典型持续过程包括：
   - AI驱动的角色处理自己的事务
   - 陷阱检查它们是否应该困住某个人
   - 银行收取并关注利息等
4. 一次性事件的发生条件（非持续过程）：
   - 玩家动作直接或者间接的后果
   - 某个过程检测到了一个待定的情况
   - 示例：赛跑中选手冲过了终点线

### 第三步：回合制游戏核心机制设计要点——无人工对手情况

1. 核心机制不做任何事情，直到玩家开始操作
2. 玩家完成动作后，核心机制计算动作对游戏世界的影响
3. 玩家等待时核心机制保持空闲
4. 同步输入变体：所有玩家在核心机制空闲时同时输入动作，完成后核心机制统一计算所有玩家动作效果
5. 设计特征：更像是对事件结果的说明，而不是所有时间内都在运转的过程的集合
6. 必须说明：每一个可能动作的影响和行为结果会发生其他什么样的计算
7. 关键约束：它们只在玩家轮转之间发生
8. 特殊要求：在对过程的设计中一定要指出哪一个过程可以安全地被下一个玩家的轮次打断

### 第四步：回合制游戏核心机制设计要点——有人工对手或NPC情况

1. 核心机制不会在回合之间保持完全闲置
2. 必须计算人工角色/NPC的行为
3. 人工角色仍然轮流，同玩家一样（即NPC也有其回合）

### 第五步：设计文档差异总结

- **实时游戏**：描述持续运转的过程集合
- **回合制游戏**：描述玩家轮转之间发生的事件结果和可打断的过程

## 核心机制文档细节程度权衡

### 识别两种极端及其后果

**极端A：过度详细（按分钟记录，无遗漏细节）**
- 表面好处：程序员可快速转化为代码
- 实际后果：设计师被大量工作困扰，导致项目推迟或取消

**极端B：过度模糊（留下太多不清楚的地方）**
- 后果1：程序员频繁询问细节，减慢进度
- 后果2：程序员自行猜测，可能做出与设计师初衷不同的假设
- 后果3：调整阶段发现错误，返回纠正耗时巨大

### 决策原则：根据机制熟悉度选择细节程度

**高熟悉度机制 → 使用一般语言/传统惯例**
- 条件：游戏包含非常普通的场景，且相信程序员知道你的意思

**示例对比**：
- 过度详细写法："当一辆车的圈数属性超过500时，就把那辆车的胜利资格标志设置为TRUE。持续检测所有的汽车来看看那些有资格获胜的汽车的位置属性是否位于或者超过了终点线。把获胜者实体设置为位置属性第一个满足条件的汽车的号码。"
- 推荐写法："第一辆完成所有的500圈并通过终点线的汽车就是胜者。"

**低熟悉度/反常规机制 → 详细说明**
- 触发条件：机制别人越不熟悉，或与惯例背道而驰

**示例1：飞镖游戏《301》**
- 反常规点：玩家从有分数开始，减去击中靶数，目标为零分
- 常规：通常是从零开始累加分数
- 要求：需要更详细解释

**示例2：完全想象出来的实体（如母龙）**
- 原因：无人可依靠已存经历知道其行为方式
- 要求：需要更详细的说明

### 推荐工具：伪代码

- 适用场景：需要详细解释的过程
- 定义：包含if和while语句说明条件或重复操作，但无真正程序的变量名或语法特征
- 前提：设计师需具备基础编程知识（至少学习一门包含条件和重复执行概念的语言）

### 协作建议：早期获取程序员反馈

- 时机：核心机制设计过程的早期阶段
- 目的：帮助发现遗漏的或忘记记下的细节

## 关键变量

| 变量名 | 类型 | 描述 |
|--------|------|------|
| hybrid_structure | enum | 混合结构：主从模式 vs 融合模式 |
| primary_genre | string | 主要游戏类型 |
| secondary_genre | string | 次要/迷你游戏类型 |
| authenticity_check | boolean | 混合是否出于游戏本质需要而非强行差异化 |
| target_audience_representative | entity | 目标受众代表，用于早期验证 |
| game_time_system | enum | 时间系统类型：实时(real-time)或回合制(turn-based) |
| has_ai_opponents | boolean | 是否存在人工对手或NPC |
| simultaneous_input | boolean | 回合制中是否采用同步输入模式 |
| interruptible_processes | list | 回合制中可被下一玩家轮次打断的过程清单 |
| mechanism_familiarity | string | 评估目标读者对该机制的熟悉程度 |
| consistency_with_convention | boolean | 是否与行业常规做法一致 |
| programmer_background | string | 程序员对游戏领域的了解程度 |

## 输出结果

生成混合类型设计方案，包含：
- 类型组合合理性验证
- 早期受众测试计划
- 真实性检查清单
- 若存在强行混合风险则触发重新设计警告

根据游戏类型输出对应的核心机制设计框架：
- 实时游戏：输出持续过程清单
- 回合制游戏：输出事件结果说明模板，并标注需指明可打断的过程

根据机制特性选择适当的文档细节程度：
- 常规场景：用自然语言
- 反常规/陌生场景：用详细说明或伪代码
