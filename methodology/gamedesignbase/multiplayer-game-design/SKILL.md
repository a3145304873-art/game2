# 多人游戏设计

## 使用场景
- 设计本地多人游戏
- 实现多人聊天系统
- 管理玩家通信行为
- 设计儿童安全社交环境

## 本地多人游戏设计

### 核心问题

**问题一：屏幕分割导致的视野受限**
- 根本原因: 所有玩家共享一个电视屏幕
- 技术方案:
  - 方案A（无额外屏幕）: 为每个玩家复制游戏界面，将屏幕细分为更小的窗口
  - 方案B（有额外屏幕）: 在操作台上配置额外屏幕供单个玩家使用
- 负面影响:
  - 每个玩家在独立窗口中比全屏幕窗口更难看得清楚
  - 其他玩家在其游戏窗口中的活动会使得玩家分心

**问题二：信息无法隐藏的隐私缺陷**
- 根本原因: 本地玩家使用同一个显示设备，无法隐藏信息
- 结果: 每个玩家都能看到其他人做的任何事情
- 适用性差异:
  - 适用场景: 打斗游戏（能够很好地运行）
  - 不适用场景: 战争游戏（玩家们可能想对自己的活动进行保密）

**问题三：玩家人数的硬性上限**
- 控制台游戏: 很少支持超过四人以上玩家
- 个人计算机: 支持的人数更少
- 超限后果:
  - 显示层面: 屏幕将会被角色和其他的数据挤满
  - 性能层面: 机器本身也会因为计算任务的增加而陷入死机

### 任天堂的差异化解决方案

1. **Wii U方案**
   - Wii U手柄作为输入装置
   - 包括一个屏幕，可以显示只有玩家能够看到的秘密信息

2. **早期方案（游戏盒子/GBA）**
   - 只允许玩家将插入一个GBA，通过它来进行控制

3. **任天堂DS系列方案**
   - 通过手机进行无线连接
   - 支持在个人的手机上进行多人本地游戏

## 多人游戏聊天系统设计

### 基础功能构建
- 必须包含聊天功能，使玩家能够互相发送信息
- 支持多种输入方式:
  - 键盘输入（文本聊天）
  - 微型话筒输入（语音聊天）

### 消息类型与通信范围设计

**消息类型**
- 私人信息: 发送给另一个特定玩家
- 团队信息: 发送给自己的团队
- 普通公开信息: 供因某种原因有兴趣查看的玩家看到

**通信范围**
- 附近的人
- 团队人员

**位置无关性原则**
- 无论玩家在游戏中的物理位置或虚拟位置如何
- 都必须能够给团队人员发送公开信息

### 行为管理与秩序维护

**识别潜在问题**
- 聊天可能带来暴力、谩骂或者骚扰行为

**满足用户期望**
- 付费玩家期望其他玩家具有最低限度的礼仪

**特殊受众考量**
- 为了使游戏能被孩子们接受
- 必须满足家长让孩子远离谩骂或冒犯行为的要求

**监督机制设计**
- 参考体育比赛中的裁判机制，根据特定准则维持秩序
- 如果没有设置裁判，则必须满足其他玩家集体的权益
- 网络上监督玩家行为比线下更加困难

## 预定义聊天限制机制

### 适用场景
- 目标用户群体为儿童
- 需要绝对安全的聊天环境

### 实施方案

1. **功能移除**
   - 完全移除语音聊天功能
   - 完全移除自由文本输入功能

2. **提供选项**
   - 仅允许玩家从系统预设的、经过审核的词句列表中进行选择

3. **环境定位**
   - 明确游戏环境面向儿童
   - 示例: 《马里奥赛车》、《网娃》

4. **安全保证**
   - 确保玩家无法输入或说出任何冒犯性言语

5. **局限性评估**
   - 认识到该方式无法满足成年人聊天的社会需求

## 设计决策流程

### 1. 确定多人游戏类型
```
IF 本地多人游戏
THEN 考虑屏幕分割、信息隐藏和人数限制

IF 在线多人游戏
THEN 考虑聊天系统和行为管理
```

### 2. 评估信息保密需求
```
IF 游戏需要隐藏玩家信息
THEN 避免本地多人游戏
或使用额外屏幕方案（如Wii U）

IF 信息公开不影响游戏体验
THEN 本地多人游戏可行
```

### 3. 确定聊天安全级别
```
IF 目标用户为儿童
THEN 使用预定义聊天限制机制

IF 目标用户为成年人
THEN 实现完整聊天功能和行为管理
```

### 4. 选择监督机制
```
IF 资源充足
THEN 设置裁判系统

IF 资源有限
THEN 依赖玩家集体权益和举报机制
```
