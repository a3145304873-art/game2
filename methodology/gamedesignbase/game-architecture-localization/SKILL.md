# 游戏架构与本地化

## 使用场景
- 设计游戏核心机制
- 规划游戏本地化策略
- 确保游戏可移植性
- 管理文本资源和代码分离

## 核心机制与硬件分离设计原则

### 设计约束
- 在设计核心机制时，**避免**将设计要点建立在特定的输入/输出（I/O）器件的性能特征上

### 职责分配
- 让UI（用户界面）来管理硬件
- 保持游戏硬件的内部独立

### 架构目标
- 核心机制不应直接依赖特定硬件

### 实施益处
- **移植性**: 若将来将游戏移植到另一台机器上，只需重新设计UI，而不必重新设计游戏的核心机制

## 文本与代码/图像分离原则

### 核心原则：绝对分离

**禁止操作**
- 绝不要让程序员把文本构建到程序代码中（硬编码）
- 绝不要在图像中构建希望玩家阅读的文本
  - 纹理（textures）中的文本
  - Shell菜单背景中的文本
  - 任何图片格式的文本

**正确做法**
- 把所有的文本存储在一个或多个文本文件中
- 使用外部化文本文件管理所有可阅读内容

### 技术原因
- 编辑文本文件非常简单（文本编辑器即可）
- 编辑图片中的文本非常困难（需要图像编辑软件，重新渲染，可能影响画质）
- 分离后翻译人员无需接触代码或图像资源即可完成工作

### 实施检查点
- [ ] 审查所有代码文件，确保无硬编码字符串
- [ ] 审查所有图像资源，确保无关键文本信息

## 装饰性文本例外规则

### 例外条件判定（必须同时满足）
- 条件A: 文本纯粹当作修饰用（decorative purpose only）
- 条件B: 不希望玩家阅读该文本
- 条件C: 不希望玩家理解该文本的意思
- 条件D: 文本不包含关键线索（key clues）

### 典型示例
- 以纽约为背景的游戏中的广告牌
- 广告牌用英语书写（与纽约环境一致）
- 即使游戏本地化为其他语言，这些广告牌仍保留英文
- 原因: 保持场景的真实性和沉浸感

### 关键判定标准

**检查文本是否包含关键线索**
```
IF 包含解谜提示
THEN 必须翻译

IF 包含任务信息
THEN 必须翻译

IF 影响游戏进度
THEN 必须翻译

IF 不包含关键线索
THEN 可保留原文
```

### 风险警告
- 必须严格审查确保无关键信息遗漏
- 建议在游戏设计文档中明确标注哪些文本属于装饰性例外

## 架构设计流程

### 1. 核心机制设计阶段
```
IF 设计核心机制
THEN 应用分离原则
- 避免依赖特定I/O设备特征
- 让UI层管理硬件交互
- 保持核心逻辑硬件独立
```

### 2. 文本资源管理阶段
```
IF 游戏包含需要本地化的文本
THEN 必须将文本存储在文本文件中
- 禁止嵌入代码
- 禁止嵌入图像
- 使用外部化文本文件
```

### 3. 文本分类阶段
```
FOR 每个文本元素
  IF 纯粹装饰 AND 无关键线索
  THEN 保留原始语言
  ELSE
  THEN 必须翻译
```

### 4. 实施验证阶段
```
- 审查代码文件，检查硬编码字符串
- 审查图像资源，检查嵌入文本
- 验证文本文件完整性
- 确认装饰性文本标注
```

## 最佳实践

### 早期规划
- 在开发早期确立文本分离原则
- 在架构设计阶段考虑硬件分离
- 建立文本资源管理规范

### 文档管理
- 明确标注装饰性文本例外
- 维护文本资源映射表
- 记录强制绑定和关键线索

### 团队协作
- 程序员: 避免硬编码，使用外部文本资源
- 美术: 避免在图像中嵌入可读文本
- 设计师: 明确标注装饰性文本和关键线索
- 翻译: 仅操作文本文件，无需接触代码和图像
