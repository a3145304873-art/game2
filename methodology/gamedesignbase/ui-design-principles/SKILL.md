# UI设计原则

## 使用场景
- 游戏过程过于复杂，无法单独用控制器按钮完成
- 需要设计屏幕按钮和菜单系统
- 实现按键重设置shell菜单
- 设计用户界面交互

## 屏幕按钮和菜单设计

### 适用场景判断
```
IF 游戏过程过于复杂 AND 无法单独用控制器按钮完成
THEN 使用屏幕按钮和菜单
```

### 输入设备选择
- **最适合**: 鼠标作为点击设备
- **备选**: D-pad（方向键）或操纵杆

### 平台差异考量
- **控制台**: 没有鼠标，较少使用屏幕按钮和菜单
- **PC**: 广泛使用屏幕按钮和菜单
- 影响: 控制台游戏通常比PC游戏简单

### 关键设计原则

1. **避免迷惑**
   - 过多的屏幕按钮和菜单可能使玩家迷惑
   - 临时玩家可能更不容易接受

2. **保持沉浸性**
   - 除非使用桌面视角，否则避免让按钮和菜单与普通计算机界面相似
   - 游戏看起来与其他应用程序越相似，越损害沉浸性
   - 基于屏幕的控制和整体视觉主题应互相符合

## 按键重设置Shell菜单设计

### 核心功能要求
- 允许玩家把动作指定为他们更喜欢的按键
- 适用于几乎所有游戏动作（特殊强制绑定除外）

### 菜单快捷键设置
- 允许玩家设置菜单的快捷键
- 目的: 让玩家可以不通过鼠标快速选择菜单项

### 强制绑定要求
- 识别必须强制绑定的核心动作（如射击游戏中的射击动作）
- 实现验证: 如果玩家没有设置这些强制动作，不允许退出shell菜单
- 目的: 确保游戏基本功能可用

### 界面显示要求（关键设计规范）

**必须显示**
- 所有的当前设置
- 所有没有指定按键的游戏特性
- 同一屏幕上当前所有没有指定的按键

**禁止设计**
- 不要让玩家为了设置按键而从一个屏幕切换到另一个屏幕
- 要求单屏完成配置

### 配置保存要求
- 在游戏中保存玩家的定制
- 玩家不用每次玩游戏时都重新设置

### 高级功能

1. **多配置文件**
   - 让玩家把不同的设置保存在单独命名的文档中

2. **多用户支持**
   - 每一个玩家都可以有自己的定制设置

3. **恢复默认**
   - 包含一个恢复默认选项
   - 玩家可把定制改回原始设置

## 设计检查清单

### 屏幕按钮和菜单
- [ ] 确认游戏复杂度需要屏幕按钮和菜单
- [ ] 选择合适的输入设备（鼠标优先）
- [ ] 避免过多按钮导致玩家迷惑
- [ ] 保持视觉主题一致性，避免破坏沉浸性

### 按键重设置菜单
- [ ] 支持几乎所有游戏动作的按键绑定
- [ ] 识别并强制绑定核心动作
- [ ] 单屏显示所有配置信息
- [ ] 实现配置保存功能
- [ ] 支持多配置文件和多用户
- [ ] 提供恢复默认选项
