# 游戏开发生命周期管理

## 何时使用
- 开始设计游戏且游戏规模非极小
- 需要确定开发阶段和任务边界
- 判断是否进入调整阶段（功能锁定）
- 规划关卡设计启动时机
- 管理开发里程碑

## 执行步骤

### 1. 应用三阶段开发模型

**阶段一：概念设计阶段（Concept Stage）**
- **执行顺序：** 最先执行
- **核心特征：** 结果一旦确定不会改变
- **关键决策内容：**
  - 游戏概念（concept）
  - 目标人群（target audience）
  - 游戏类别（game genre）
- **重要性：** 这些选择必须在开始一次确定好，以后不能再改

**阶段二：详细设计阶段（Elaboration Stage）**
- **核心任务：** 加入大部分设计细节
- **验证方法：** 通过原型化方法（prototyping）和游戏测试（playtesting）
- **关键特性：** 可以重新定义设计决定，允许迭代修改
- **与旧模式区别：** 不同于20世纪80年代先创建完整文档再编写代码的方式

**阶段三：调整阶段（Tuning Stage）**
- **核心限制：** 不能再加入新的特征（no new features）
- **允许操作：** 只能为优化游戏做些小的调整（small adjustments for optimization）

### 2. 判定调整阶段进入条件

**阶段识别标志：**
- 游戏概念（基础）已在前期确定
- 细化设计阶段已充实概念并添加新功能
- 整个设计的交付时间已提前规定
- 没有更多的功能可以添加到游戏当中

**阶段转换判定（"功能锁定"）：**
- **核心标准：** 日程表决定——如果剩余时间将全部用于"完成和修复游戏bug"
- **关键信号：** 设计师不能再添加任何更多的设计，否则项目就要延期
- **本质特征：** 这不是主动解决问题的方法，而是被动接受的结果

**理想锁定时机：**
应该在"游戏设计已经完整且和谐的时候"便进行锁定，这样有更多的时间进行其他的设计工作。

### 3. 确定关卡设计启动时机

**启动时机判断：**
- 不必等待所有组件完全设计完成
- 但必须完成"一定程度"，足以供关卡设计师参考
- 可用的参考组件包括：角色、挑战、动作、游戏世界、核心机制、故事情节（如果有的话）

**代表关卡选择原则（关键决策）：**
- **错误选择：** 玩家遇到的第一个关卡
  - 原因：第一关通常非常简单，因为玩家仍在学习游戏
  - 第一关通常作为教程关卡，不能代表游戏完整可玩性
- **正确选择：** 游戏中"更远的一关"
  - 标准：该关卡已经包含了大多数的游戏可玩性
  - 目的：能够真正展示游戏的核心体验和设计意图

**里程碑意义：**
创建一个可工作的游戏关卡是游戏开发中一个重要的里程碑，这意味着测试者可以开始进行游戏测试了。

### 4. 调整阶段的核心工作

**允许的操作：**
- 对游戏的关卡和核心机制进行"微调"
- 微调游戏的平衡性

**禁止的操作：**
- 引入任何新功能
- 加入新的铃声和口哨（新元素）

**核心原则：**
- 打磨是一个"做减法的过程，而不是加法"
- 消除多余的瑕疵，使游戏光彩照人
- 调整和打磨游戏，直到它"至臻至美"

## 整体开发原则

- 大型游戏的设计和构建是一个反复的过程（iterative process）
- 整个开发过程中需要不停地测试和调整（continuous testing and adjustment）
- 不时地修改设计（frequent design modifications）
- 但并非所有部分都需要返工（not all parts need rework）

## 设计检查清单

- [ ] 概念阶段已锁定核心决策（概念、目标人群、类别）
- [ ] 详细阶段通过原型化和测试验证设计
- [ ] 调整阶段已停止添加新功能
- [ ] 调整阶段专注于微调和平衡性优化
- [ ] 关卡设计在组件完成"一定程度"时启动
- [ ] 代表关卡选择非第一关的典型关卡
- [ ] 已创建可工作的里程碑关卡用于测试
