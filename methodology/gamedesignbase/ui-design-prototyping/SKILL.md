# 用户界面设计与原型构建

## 适用场景
- 需要记录游戏用户界面设计
- 需要设计实际用户界面并验证设计运行情况
- 已确定UI元素名称和功能
- 需要向开发团队传达UI设计规范

## 前置条件
- 已定义的游戏模式
- Shell 屏幕列表
- 用户界面元素列表
- 已设计好的UI元素名称和功能

## 工作流程

### 第一阶段：编写UI设计文档

**1. 文档目标**
- 用户界面通过图形、音频、文本和软件创建玩家体验
- 需特别清楚地记录以便整个开发团队处理

**2. 覆盖范围**
- 必须针对每种游戏模式进行描述
- 必须针对所有 shell 屏幕进行描述

**3. 必须包含的核心要素**
- 屏幕的布局
- 虚拟相机的行为
- 输入设备的功能
- 游戏将提供的任何可听反馈

**4. 综合考量**
- 文档内应包括美学方面的考虑
- 文档内应包括技术方面的考虑
- 文档内应包括可用性方面的考虑

**5. 文本处理**
- 任何作为用户界面一部分出现的文本，必须详细收录在屏幕文本文档中
- 必须附带简要描述

### 第二阶段：构建UI原型

**1. 准备阶段**
- 确认已拥有设计好的模式的UI元素的名字和功能

**2. 工具选择与构建**
使用最少编程工作的工具制作包含图形和声音的界面原型：

**简单原型**
- 在 Microsoft PowerPoint 中使用超链接使幻灯片之间切换

**高级功能**
- 使用 Adobe Flash

**游戏工具**
- 若具备编程能力，使用 Blitz Basic 等游戏制作工具

**手机游戏**
- 使用索引卡制作纸上模型并进行试玩

**3. 资源投入控制**
- 使用正在运行的美术作品和声音构建原型以查看设计运行情况
- **不要**假设会在最终产品上使用它
- **不要**在美术或声音上花费过多时间（若计划改变，可能会抛弃）

**4. 功能实现标准**
- 原型不是可玩的游戏，而是显示菜单和屏幕按钮并对输入设备信号做出反应
- 应在没有游戏软件支持的情况下尽可能准确地做出反应：
  - 若菜单项引起转换到新的游戏可玩性模式，必须把该模式构建到其中
  - 若控制器按钮可以发射激光，构建的原型至少应发出"磁"的声音来确认按下

**5. 迭代开发与测试**
- **不要**一次构建所有的模式
- 采用"构建一点 -> 测试 -> 调整 -> 添加更多模式"的循环
- 在设计并向原型中加入额外的游戏可玩性模式时，坚持测试以观察是否达到要求

**6. 设计策略**
- 一般来说从最好的那款游戏中借鉴即可
- 不要盲目创新除非不得不这样做

## 输出成果
- 完整的UI设计文档，包含布局、相机、输入、反馈及美学考量
- 可交互的UI原型
- 测试反馈和迭代记录

## 注意事项
- 不适用于非用户界面相关的底层代码逻辑
- 不要在美术或声音上花费过多时间（假设最终不使用）
- 不要一次构建所有的模式
- 不要盲目创新（除非不得不这样做）
