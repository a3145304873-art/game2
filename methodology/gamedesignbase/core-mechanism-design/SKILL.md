# 核心机制定义与设计

## 何时使用

- 需要将抽象挑战转化为具体可玩机制
- 拥有实体列表和动词列表，需要定义系统规则
- 设计游戏内部经济、物理、进展等系统
- 详细设计阶段，将概念具体化为可执行规则

## 核心机制定义

核心机制确定游戏实际的运作方式，包含：
- **规则系统**
- **玩家交互方式**

**核心作用**：创造娱乐体验。

## 五类核心机制

| 类型 | 描述 | 典型应用 |
|-----|------|---------|
| 物理机制 | 模拟现实或虚构的物理法则 | 运动、碰撞、重力、动量 |
| 内部经济机制 | 资源的产生、流通和消耗 | 货币系统、资源管理 |
| 进展机制 | 能力/状态/内容随时间变化 | 升级系统、解锁内容、技能树 |
| 战术机动机制 | 策略选择和位置决策 | 空间关系、时机把握 |
| 社交互动机制 | 玩家间及与NPC交互规则 | 合作、竞争、交易、沟通 |

## 设计流程

### 第一阶段：处理设计文档模糊表述

将模糊句子转化为详细说明：
- ❌ "玩家获得金钱" / "获得若干金钱"
- ✅ 明确：金钱实体何时增加、增加多少

### 第二阶段：思考资源流动（资源层面）

1. 从资源开始，分析流动方式：
   - **来源**：什么机制把资源带入游戏？
   - **消耗**：什么机制把资源移除出游戏？
   - **转换**：资源可以交易或自动转换为另一种资源吗？

2. 每个来源、消耗、转换需定义：
   - 转换的运行方式
   - 转换发生的时间
   - 转换发生的速度

3. 考虑资源用尽情况：
   - 问："当资源用尽时会发生什么？"
   - 若无变化，则可能不需要该资源

**关键特性**：资源是一般概念，不是具体量。通过思考经济中的流动即可确定很多资源机制。

### 第三阶段：研究实体（实体层面）

对每个实体逐一回答：

| 检查项 | 问题 |
|-------|------|
| 存储资源检查 | 该实体是否存储资源？运行方式是否已记录？ |
| 被动影响检查 | 什么事件/过程/关系影响该实体？适用什么条件？ |
| 主动影响检查 | 该实体影响什么？适用什么条件？ |
| 自主行为检查 | 实体自己能做什么？（简单如检测器，复杂如NPC） |
| 玩家操作检查 | 玩家可以对实体做什么？需要什么动作和机制？ |
| 符号实体检查 | 如何进入每一种可能的状态？ |

### 第四阶段：动词-实体关联核查

- 检查动词列表中的动词与特定实体的关联
- 核查哪个动词适合该实体
- 分析这些动词暗示了什么机制

## 挑战类型与机制设计路径

| 挑战类型 | 设计路径 | 关键参数 |
|---------|---------|---------|
| 数值积累类 | 定义来源系统 → 定义获取行为 → 数值经济平衡 | 收入速率、支出需求、稀缺性控制 |
| 物理运动类 | 定义运动特征参数体系 → 定义其他必需元素 | 速度、力量、加速度、准确度 |
| 符号关系类 | 定义符号系统 → 定义操作规则集 | 符号类型、操作方式、触发条件、判定逻辑 |

## 生命周期与定位管理

| 阶段 | 形式 | 关键动作 |
|-----|------|---------|
| 初始设计 | 设计文档中的自然语言 | 记录算法 |
| 原型验证 | 电子表格（算法+数据混合）或纸质原型 | 试玩验证体验 |
| 最终实现 | 代码算法 + 数据文件 | 程序员实现，设计师提供规格 |
| 修改维护 | 同步更新代码和文档 | 重大改变必须记录，供测试团队使用 |

## 与关卡设计的交互

**职责分离原则**：
- **关卡设计**：指定挑战的类型、时机和结果
- **核心机制**：指定不同挑战的工作方式

**乐高积木类比**：核心机制创造基础功能供关卡设计师构建关卡。

## 输出标准

完整的游戏机制定义文档，包含：
- 资源来源/消耗/转换机制
- 每个实体的完整机制定义
- 动词-实体关联机制
- 挑战-机制映射表
- 具体参数设定
- 玩家输入-系统响应逻辑链

## 约束条件

- **不适用**：纯叙事无交互机制的游戏
- **不适用**：完全随机无规则的游戏
- 设计师不必会编程，但必须知道算法的大概过程
