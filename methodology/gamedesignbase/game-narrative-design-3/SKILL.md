# 游戏叙事设计

## 使用时机
- 需要在游戏中插入非交互式内容来讲述故事部分
- 需要确定叙事块位置、时长或形式
- 设计目标为控制叙事体验并降低开发复杂度
- 需要确保故事逻辑严密性和情感冲击力
- 游戏具有玩家选择机制
- 玩家的动作和选择对故事走向有影响
- 需要设计故事结局

## 电子游戏叙事块（非交互式情节）设计规范

### 确定叙事块放置位置类型

#### 类型A【开幕插曲】
- 放置于游戏开始
- 作为介绍故事的开幕
- 建立游戏世界背景
- 示例：《半条命》以电影片段开始，展示玩家化身戈登·弗里曼驾驶有轨电车穿过Black Mesa联合研究所，同时有声音解释角色背景，设置后续体验舞台

#### 类型B【结尾情节】
- 放置于玩家完成游戏时
- 作为包装好故事的结局

#### 类型C【关卡间过渡】
- 放置于关卡（章节或任务）之间
- 采用简短说明形式介绍下一关情节

#### 类型D【场景插叙/Cut-scenes】
- 嵌入游戏过程中
- 暂时打断游戏的短小非交互式情节

### 应用基础时长设计规则（基于放置位置）

#### 对于类型C（关卡之间）
- 标准时长范围为30秒至4分钟或5分钟

#### 对于类型A和B（开始/结束）
- 允许超过5分钟
- 参考案例：《光晕2》中叙事场景时长超过5分钟
- 因其向整个游戏体验提供重要叙事支撑

#### 对于类型D（游戏过程中）
- 必须保持简短
- 因其会打断玩家动作的流畅性和节奏

### 应用类型D（场景插叙）的 genre-specific 时长调整规则

#### 若目标游戏为【快速移动类别】
- 实时策略游戏RTS
- 动作冒险游戏
- 严格限制时长
- 避免让玩家听或观看时间过长而不让做事情
- 否则玩家会感到厌烦

#### 若目标游戏为【移动较慢类别】
- 冒险游戏
- 角色扮演游戏RPG
- 可允许较长时间
- 因此类玩家可以更好地忍受长时间的场景插叙

## 电子游戏线性故事设计原则与权衡

### 概念定义与分类

**线性故事（linear story）**
- 玩家不能改变情节或故事结局的叙事结构
- 与"非线性故事"（玩家可改变情节/结局）相对

**交互特性**
- 玩家面临挑战并执行动作
- 但这些动作仅推动预设情节发展
- 不改变故事走向或结局

### 典型应用案例分析

#### 《半条命》（Half-Life）
- 讲述线性故事
- 故事结局玩家不能改变
- 但玩家执行了大量作为故事组成部分的动作

#### 《星际争霸》（StarCraft）
- 各任务之间的叙事块（narrative blocks）成为玩家完成任务的奖励
- 整体故事保持线性发展

### 设计优势详细分析

#### 3.1 内容制作与资源需求
- 仅需创作固定顺序事件的素材
- 无需准备分支剧情内容
- 开发时间和资金需求显著降低（相比非线性故事需要准备多种情节变体）

#### 3.2 技术实现与引擎复杂度
- 故事讲述引擎只需跟踪单一情节事件序列（single sequence of plot events）
- 无需记录玩家做出的重要决定（因为不存在此类决定）
- 软件实现更简单
- 测试故事讲述引擎需要的时间大幅减少（许多开发者因测试复杂的非线性引擎而失败）

#### 3.3 一致性与错误控制机制
- 事件序列保持不变，可保证故事逻辑严密性和意义完整性
- 避免"连续错误"（continuity errors）：即给定前提事件下，因叙事材料未随游戏事件改变而导致物体外观与应有状态不一致的错误
- 状态一致性示例：若汽车损坏是故事的一部分，则它应该一直保持损坏状态；若故事要求汽车完整，则不必给玩家提供损坏它的任何方式，从而避免非线性故事中可能出现的逻辑矛盾

### 设计限制与约束条件

#### 4.1 戏剧性自由（dramatic freedom）缺失
- 玩家拥有操作自由但无戏剧性自由
- 动作除了让故事前进，不应影响其他部分
- 游戏可玩性必须服从叙事需求：如果故事始终要求有一个完整的汽车，那么游戏就不允许玩家损坏这辆汽车

#### 4.2 玩家 agency 限制
- 无法提供改变故事走向的决策点
- 交互仅限于执行动作（action execution）而非情节改变（plot alteration）

### 情感表达与创意优势

- 能够驾驭更加巨大的情感力量（greater emotional power）
- 这是线性故事在创意角度上的最大优势之一
- 适用于20世纪90年代对非线性故事实验的恐慌之后，游戏产业恢复使用的主流设计模式

### 实施架构建议

- 若希望讲述逻辑严密的线性故事，应将所有故事作为"旅行"（journey）来看待
- 设计时需确保游戏机制（mechanics）与叙事需求严格对齐
- 防止玩家行为破坏预设情节

## 多结局设计的使用条件

### 评估玩家被赋予的戏剧性自由程度

- 检查游戏中玩家是否拥有 meaningful choices（有意义的选择）
- 确认玩家的动作和选择是否真正影响故事走向

### 判断多结局的必要性（决策树）

#### 情况A：玩家拥有大量戏剧性自由
- 即玩家的选择对故事有实质性影响
- → 应该设计多个结局，以兑现"玩家选择很重要"的承诺

#### 情况B：玩家没有获得很多戏剧性自由
- 即游戏是线性叙事，玩家选择有限
- → 没有理由设计多个结局，保持单一结局即可

### 结局数量与选择重要性的匹配原则

- 你给玩家选择的重要程度越高 → 必须创造的结局数量越多
- 你给玩家选择的重要程度越低 → 需要的结局数量越少

### 核心原则总结

#### "信守诺言"原则
- 如果你告诉玩家她的动作特别是她的选择对结局很关键，那么应该兑现这个承诺

#### "任何可以获得的结局"原则
- 给玩家的动作提供任何逻辑上可能达成的结局

## 关键变量

| 变量名 | 类型 | 描述 |
|--------|------|------|
| narrative_block_type | enum | 叙事块类型：开幕插曲、结尾情节、关卡间过渡、场景插叙 |
| placement_location | string | 具体放置位置：游戏开始、游戏结束、特定关卡之间、游戏过程中 |
| game_genre_pace | enum | 游戏节奏类别：快速移动（RTS、动作冒险）、移动较慢（冒险、RPG） |
| recommended_duration_range | string | 建议时长范围，如'30秒-5分钟'或'简短' |
| plot_sequence_fixedness | boolean | 事件是否按预设顺序发生且不可改变 |
| story_engine_complexity | enum | 跟踪单一序列(低) vs 跟踪多分支(高) |
| continuity_error_risk | risk_level | 因状态不一致导致叙事逻辑破裂的可能性 |
| dramatic_freedom_degree | degree | 玩家动作对故事发展的影响程度，线性故事中为0 |
| dramatic_freedom_level | qualitative_scale | 玩家在游戏中做出影响故事的选择的自由度，分为高/低两个等级 |
| choice_importance_promise | boolean | 游戏是否向玩家明示或暗示其选择对结局至关重要 |
| ending_dramatic_significance | boolean | 每个结局是否具有独立的戏剧价值和情感冲击力 |

## 输出结果

基于放置位置和游戏类型，输出叙事块的具体形式（开幕/结尾/过渡/插叙）、建议时长范围（精确到秒或分钟）、以及是否需要特别缩短的警告标识

采用线性故事结构的设计决策，包含：
- 内容制作成本评估(低)
- 技术实现方案(单一序列跟踪)
- 一致性保障机制(禁止改变关键对象状态)
- 情感表达最大化策略

判断结果：应该/不应该设计多个结局；若应该，则根据选择重要性确定具体结局数量
