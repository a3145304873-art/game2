# 游戏开发流程管理

## 使用场景
- 将抽象游戏概念转化为可执行方案
- 向大型团队/出版商传达设计意图
- 建立开发流程
- 评估开发工作优先级
- 提升游戏乐趣和品质

## 核心概念

### 游戏想法 vs 设计决策

#### 游戏想法（抽象阶段）
- 高层次的意图陈述
- 过于笼统，无法直接实施
- 缺乏可执行的具体细节和测量标准

#### 设计决策（具体化阶段）
- 包含具体参数、条件和行为的可执行规格
- 从模糊意图变为具体可编程逻辑

### 乐趣贡献因素优先级

1. **首要因素**：避免基本错误（最重要）
2. **第二重要**：调整和完善
3. **前提条件**：富有想象力的变化
4. **5%的工作**：游戏创新
5. **不可控因素**：运气/魔力/幻觉

## 执行步骤

### 步骤1：理解设计文档的五大核心目的

#### 1. 决策记录与知识保持
- 记录会议中或午餐时间做出的设计决定
- 防止遗忘和重复讨论
- 确保团队成员对决定有共同记忆基础

#### 2. 将泛泛而谈转化为具体文章
- 将模糊概念细化为可执行规格
- 回答实施层面的具体问题
- 确保设计足够详细以产生具体形象

#### 3. 跨团队意图传达与任务规划
- 适用于大型商业游戏（数百人团队）
- 替代持续的电话沟通
- 使各部门能计算执行计划所需的时间和人力资源

#### 4. 合同义务与里程碑基础
- 作为开发合同中可交付成果里程碑的法律基础
- 支持提前制订时间表
- 提供详细功能规格

#### 5. 向供货机构提供能力证据
- 向出版商和资金提供方证明开发团队知道自己在做什么
- 展示资金用途，建立付费方信心

### 步骤2：将抽象想法转化为设计决策

#### 转化示例：龙守护蛋

**游戏想法**：龙应该保护它们的蛋

**设计决策**：
- **前提条件**：龙的巢中有蛋时生效
- **警戒机制**：母龙不会让她的巢穴离开视线范围
- **触发阈值**：敌人闯入距离巢穴50米之内时触发
- **行为响应**：龙会停止任何其他活动并立即返回巢穴
- **持续条件**：一直守护直到敌人离开方圆50米的范围至少30秒以上
- **优先级规则**：龙会尽最大努力保护蛋

**关键转化标志**：从"应该保护"变为"50米距离+30秒持续时间"

### 步骤3：按优先级处理开发工作

#### 优先级1：避免基本错误
- 糟糕的编程
- 糟糕的音乐和声音
- 糟糕的美工
- 糟糕的用户界面
- 糟糕的游戏设计

**执行动作**：找到这些错误然后修复它们！

#### 优先级2：调整和完善
- 对细节进行关注
- 让所有的东西都变得完美
- 长时间的投入会让游戏和普通的游戏变得不同

#### 优先级3：富有想象力的变化
- 采用基本的游戏元素
- 达到超出想象的体验
- 关卡设计师在此方面贡献最为突出

#### 优先级4：游戏创新
- 包括游戏的原始想法和后来做出的创造性决定
- 游戏设计师的创新对游戏乐趣的贡献是很有限的

#### 优先级5：运气/魔力/幻觉
- 不可预知、不可分析、不可计算
- 不能决定它是否发生，所以不用为它费心
- 当你感觉不到它的存在时，要认真修改设计

### 步骤4：实施成本控制

#### 纠错成本优化原则
- 在写出任何代码或创建任何图形之前纠正设计错误要容易得多
- 对于PC或控制台游戏，建议在开发前分配一到六个月进行纯粹的设计工作
- 设计阶段应结合用于测试游戏玩法的原型工作

## 设计检验标准

### 设计文档检验
- [ ] 是否记录了所有设计决策？
- [ ] 是否将抽象概念转化为具体规格？
- [ ] 是否包含具体参数（距离、时间、行为条件）？
- [ ] 是否支持跨团队沟通？
- [ ] 是否满足合同要求？

### 开发优先级检验
- [ ] 是否优先修复基本错误？
- [ ] 是否投入足够时间调整完善细节？
- [ ] 是否在基础之上追求富有想象力的变化？
- [ ] 是否合理分配创新工作？

## 设计类比

### 建筑师原则
大部分游戏的设计决定都没有很多的创新空间，但创新是必要的。就像优秀的建筑师设计绝妙新建筑仍需要热量、光照和管道一样，游戏设计所需的大部分工作还是创造那些普通的且必不可少的细节。
